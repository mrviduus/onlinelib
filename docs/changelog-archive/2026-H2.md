## Reader — the dyslexic font was a saved GitHub web page on both platforms, so the setting never worked — web + mobile — 2026-08-19

`apps/web/public/fonts/OpenDyslexic-Regular.woff2` was 297,194 bytes that began with eight newlines
and then `<!DOCTYPE html><html lang="en" data-color-mode="auto"...`. It was a GitHub page, curl'd and
saved with a `.woff2` extension. `reader.css` declared it as a real `@font-face`, the browser failed
to parse it, and the "Dyslexic" reader font fell back to sans-serif — no console error, no failed
request, nothing to notice.

The mobile app inherited it by value. `apps/mobile/src/lib/openDyslexicBase64.ts` held 396 KB of
base64 of *those same bytes*, inlined into the WebView reader's `@font-face` by `readerHtml.ts`. The
decoded payload was byte-for-byte the same HTML page. So the accessibility setting had never worked
on either platform, and the mobile JS bundle carried 396 KB of a web page to achieve it.

Both now ship the real font: OpenDyslexic Regular from `@fontsource/opendyslexic` 5.3.0, SIL Open
Font License 1.1, 115,280 bytes, beginning with the `wOF2` signature. The licence text sits next to
it at `apps/web/public/fonts/OpenDyslexic-LICENSE.txt`. The mobile blob is regenerated *from* the web
file by `npm run build:dyslexic-font`, so the two platforms cannot drift apart — or, as here, ship
the same wrong thing twice. It went from 396 KB to 154 KB and started working.

Removing the feature was the other option and the cheaper one. It lost on the grounds that an
accessibility setting which silently does nothing is worse than one that is absent, and fixing it
properly turned out to cost about the same.

**Why nothing caught it for months.** A font is a static asset. No unit test opens `public/`, no
build step validates that a file with a font extension is a font, and a failed `@font-face` degrades
silently by design — that is what a fallback stack is *for*. The failure mode had no output at all.

So there are now two tests that go looking, one per platform:
`apps/web/src/styles/__tests__/fonts.test.ts` reads every file under `public/fonts` and asserts the
`wOF2` signature; `apps/mobile/src/lib/openDyslexicBase64.test.ts` decodes the base64 and asserts the
same, plus that it is not an HTML document and that its size is plausible for a font. The generator
script refuses to run against a source file that is not a woff2. Three checks, because the original
mistake was made once and then copied.

## CI — web unit tests and the whole mobile app were never checked by CI — infra — 2026-08-19

Two gaps found while wiring the font regression tests above, both of the same shape: a test suite
exists, passes, and was never run by anything except a human remembering to.

**The web suite was never in CI.** The `frontend` job ran `pnpm install && pnpm build` for web and
admin and stopped. 100 test files and 731 assertions, invisible to every pull request. A failing web
unit test merged to `main` unnoticed. It now runs `pnpm test` between the build and the overlay
drift-check. All 731 pass today, so this changes nothing about the current tree — it changes what
happens to the next regression.

**The mobile app had no job at all.** `apps/mobile` appeared in `ci.yml` exactly once, as
`pnpm check:mobile-overlay` — a drift check on a generated bundle, run from the *web* working
directory. No `tsc --noEmit`, no unit tests. A mobile type error reached `main` unnoticed, which is
an uncomfortable thing to be true of an app about to go to strangers on a closed track.

There is now a `mobile` job: `npm ci`, `npm run typecheck`, `npm test`. It is a separate job rather
than another step in `frontend` because `apps/mobile` uses npm and its own lockfile, not the pnpm
workspace. `@textstack/shared` is consumed from source through Metro `watchFolders` and tsconfig
paths, so the checkout already carries it and only the app's own dependencies need installing.

Deliberately not included: mobile e2e. `apps/mobile/e2e` is Playwright driving the Expo *web* build
in a Pixel-sized viewport. It exercises no native code path, so running it in CI would buy confidence
it cannot actually provide. (It is also 6 specs, not the 15–16 the docs claim — a separate correction.)

## Mobile — Play production plumbing: a submit profile that exists, two permissions that shouldn't, and a guard — mobile + infra — 2026-08-19

Three things stood between the Android app and a production submission, and none of them were
visible from the source tree alone.

**A submit profile that did not exist.** `eas.json` had `submit.internal` and `submit.closed`, and
`package.json` had `submit:ios` / `submit:android` scripts pointing at a `production` profile that
was never written. Both scripts had been dead since they were added. There is now a real
`submit.production` at a 10% staged rollout — `releaseStatus: inProgress` plus `rollout: 0.1`, a
fraction and not a percentage, which is the mistake this note exists to prevent. EAS cannot advance
an existing rollout, so 10 → 25 → 50 → 100 stays a Play Console action; re-submitting with a larger
number creates a second release instead of widening the first. Scripts are now named after the track
they ship to: `submit:internal`, `submit:closed`, `submit:production`.

**Two permissions that were never ours.** The app requested `RECORD_AUDIO` and
`SYSTEM_ALERT_WINDOW`, and had done so through every internal-testing build. Neither has a feature
behind it: TTS only plays audio back (`useTts.ts` sets `allowsRecording: false`), and the image
picker is avatar-only. `RECORD_AUDIO` comes from the `expo-audio` / `expo-image-picker` config
plugins. `SYSTEM_ALERT_WINDOW` comes from `expo-dev-launcher` — whose *native module* is
debug-gated, but whose *config plugin* runs at prebuild and writes into the shared main manifest, so
it lands in release builds too. Moving `expo-dev-client` around would not have fixed it.

Both are blocked now, along with `CAMERA`, using two mechanisms on purpose. The plugin props
(`microphonePermission: false`, `cameraPermission: false`) state the intent and reliably suppress the
iOS usage strings; `android.blockedPermissions` emits `tools:node="remove"` and is what the manifest
merger actually honours even if a transitive AAR reintroduces the permission.

**The verification is the interesting part.** `tools:node="remove"` in a source manifest is a
directive, not a result, so the fix was checked against the merged release manifest produced by
`./gradlew :app:processReleaseMainManifest`. All three permissions are absent there.

That merge also exposed how little the source manifest was telling us. The source lists 10
permissions; the merge produces 37. Everything the libraries contribute — `POST_NOTIFICATIONS`,
`WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED`, `USE_BIOMETRIC`, the FCM receive permission — is invisible
until the merger runs, and it is the merged set that Play shows a user.

So `scripts/check-android-permissions.mjs` reads the merged manifest when one exists and falls back
to the source with a warning. It fails the build on any permission not explicitly listed with a
written reason. It was tested in both directions before being trusted: it fails on the pre-fix
manifest, fails again on an injected `READ_CONTACTS`, and passes on the fixed one. A guard nobody has
watched fail is not a guard.

**What the guard found that the audit had not.** 22 permissions are on a WATCH list — reported on
every run, deliberately not blocked yet:

- `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, injected unconditionally by
  `expo-audio`. This app plays TTS in the foreground only — no `UIBackgroundModes`, no media
  service — so they look unused, and `MEDIA_PLAYBACK` is not free: it pulls the app into Play's
  foreground-service declaration flow, which wants a form and a demo video. They are not blocked
  blind, because if `expo-audio` starts a service internally then blocking them turns TTS into a
  `SecurityException`, and TTS is a core feature. That needs a device, not a guess.
- 20 OEM launcher and badge permissions from ShortcutBadger, pulled in transitively by
  `expo-notifications` — Samsung, Huawei, Oppo, HTC, Sony, and friends. The app never sets a badge
  count. On a reading app's listing, "read your settings" and "install shortcuts" read badly.

**Also in this change.** `expo-audio` moves from `devDependencies` to `dependencies`, where a config
plugin that is also a runtime dependency belongs — EAS installs devDependencies, so it built, but it
would have broken the first time a build set `NODE_ENV=production`. And `expo-build-properties` pins
`compileSdk` / `targetSdk` / `minSdk` to 36 / 36 / 24. targetSdk was already 36 by way of the Expo 55
version catalog, so this changes nothing today; it means a future Expo bump cannot silently move the
app off a Play-compliant target without someone approving the diff.

`typecheck` and `check:permissions` scripts exist now. CI does not run them yet — mobile's only
presence in `ci.yml` is still the overlay-bundle drift check.

Verified: `tsc --noEmit` clean, 70 unit tests pass, `expo prebuild` and the Gradle manifest merge
both succeed, guard exits 0 on the merged manifest and 1 on a rogue permission.

## Docs — CHANGELOG split into an index, an archive and postmortems — docs — 2026-08-11

The changelog had become four documents wearing one filename: a release index, a design-decision
record, an incident log, and a project-status page. 1804 lines, 379 KB, 138 entries averaging 274 words
with a 1828-word maximum, and three `##` headings in the whole file — so nothing had a closing
boundary. `docs/incidents/` did not exist. The owner's words: "I'm losing control of the project."

The cause is worth naming because it was not neglect. The original Sentry brief asked for changelog
entries rich enough to be article source material, and every subsequent entry was written to that
standard. The instruction worked exactly as written; what was missing was a *place* for that writing
that wasn't the index everyone reads first.

**Four homes now, each with one job.**

| File | Job |
|---|---|
| `CHANGELOG.md` | One line per change, grouped by deploy date. 111 lines. |
| `docs/changelog-archive/<YYYY>-H<1\|2>.md` | The full write-up behind every line, verbatim. |
| `docs/incidents/` | Postmortems. New. |
| `docs/STATUS.md` | Where the project is right now. New — nothing answered this before. |

**Nothing was deleted.** All 138 entry bodies plus both legacy release sections moved verbatim into
`docs/changelog-archive/` (2026-H1: 104 entries, 2026-H2: 34, plus pre-2026); the split was done by
script and verified by asserting every original body still appears in the archive, and by checking all
51 links and anchors resolve. Entry headings became the one-line index, so the terse file was derived
from the existing writing rather than rewritten from memory.

**Versions are CalVer** — the deploy date, `## [2026.08.11]`. TextStack ships to one production
environment on merge; there is no other version anyone could name, and semver on a product with no
consumers is ceremony.

**Eight incidents were extracted into standalone postmortems**, chosen for what they teach rather than
severity: the five-week SSG outage, both halves of the Sentry SQL leak, the 23505 upsert race, the
double-delete that destroyed a real chapter, the PDF parse that silently fell to Ollama, the RAG parse
that wedged the worker, and the backup that leaked 156 GB into its own failure. Each gets Impact, Root
cause, Fix, Lesson and — the section that matters most — **Detection: how long it took and what
actually found it.** Three of the eight were found by a screenshot, a CPU graph, or a full disk. That
pattern is only visible once they sit on one page, and `docs/incidents/README.md` names it: silence is
the symptom, the mitigation existed and was never verified, and a second egress path bypasses the first fix.

**The format is enforced where entries are written, not by intention.** `.claude/commands/pr.md`,
`.claude/commands/changelog.md`, `.claude/agents/tech-writer.md` and `.claude/commands/slice.md` all
carried "write a rich CHANGELOG entry" instructions; all four now route by kind — one line to the index,
the write-up to the archive, production breakage to `docs/incidents/`, a load-bearing decision to an ADR.
`CLAUDE.md` gains the same table. Without that change the file returns to 600-word entries inside a week,
because the instruction that produced them would still be sitting in the command files.

## SEO — static-site generation had been dead for five weeks; a forbidden HTTP header killed it — backend — 2026-08-11

> Postmortem: [`docs/incidents/2026-08-11-ssg-dead-five-weeks.md`](../incidents/2026-08-11-ssg-dead-five-weeks.md)

Started from a Bing Webmaster Tools screenshot with four warnings and ended somewhere else entirely. The warnings ("limited crawl capacity", "too many pages with insufficient content") were symptoms; Google Search Console independently agreed (`Crawled – currently not indexed: 780`, `Discovered – not indexed: 311`, `Soft 404: 67` with a validation started 15 May that never passed). Chasing the soft-404 list led to real book and author pages — Pan Michael, The Wings of the Dove, Lew Wallace — not the junk URLs an initial guess predicted.

**Root cause.** `ssg-worker.mjs` calls `http://api:8080/ssg/routes` and deliberately sets a `Host` header so `SiteContextMiddleware` can resolve the site — the file even carries a comment explaining that without it "fetch would otherwise default Host to the URL host (`api`) → 404 → silent job". That mitigation cannot work: **`Host` is a forbidden header name in the fetch spec**, so undici drops it. Verified inside the running container — `fetch` with an explicit `Host: textstack.app` still returns 404. The request arrives as `Host: api`, which is not in `site_domains`, so resolution returned null and the middleware answered `404 Site not found`. Every rebuild job failed. The worker stayed `healthy`, and the only evidence was a log line nobody was watching.

The trigger was refactor R1b, which removed the legacy `?site=` override that had been papering over this.

**Blast radius, measured.** Newest generated page: **3 July**. The sitemap is built live from the database and advertises **1153** book URLs; the generator had produced **764** pages. So roughly **389 published books returned a hard 404 to crawlers** while being actively advertised in the sitemap — which is precisely Google's `Not found (404): 153` and Bing's 140-of-1.3K index.

**Fix.** `SiteResolver` now falls back to the single site (`ICurrentSite.Id`) when the host matches no registered domain, logging a warning naming the host. This is safe in exactly the way the removed `?site=` override was not: that override could name a *different* site, producing a `SiteContext` whose Id diverged from the process-wide `ICurrentSite.Id` that EF's global query filters key on — silently yielding zero rows. Resolving to `ICurrentSite.Id` itself makes divergence impossible, and which hosts can reach the middleware at all is already constrained by `AllowedHosts`. Fixing the resolver rather than the worker also closes the class: any future internal caller that cannot set `Host` (which is every `fetch` caller) now works.

Covered by integration tests rather than unit tests, deliberately: `SiteResolver` depends on the concrete `AppDbContext`, whose model only builds on Npgsql, and the failure was inherently about a real request's host — something a mock cannot express. `SsgRouteResolutionTests` asserts `/ssg/routes` returns 200 for `Host: api`, still works for a known host, and returns a non-empty route list (an empty list would rebuild nothing while reporting success — the same silent-failure shape).

**Two pieces of misleading infrastructure found on the way, worth knowing even though they are not the bug.** `X-SEO-Render` is set from `map $is_bot`, so it reports "you look like a bot", NOT "an SSG file was served" — it says `ssg` even when the fallback ran, which cost real debugging time here. And nginx's `location /ssg/ { internal; alias …/data/ssg/; }` points at a directory that does not exist; `try_files` resolves `$ssg_file` against `root` instead, so the real pages come from `apps/web/dist/ssg` and that block is dead code whose comment asserts it is required.

**This fix alone does not restore the pages** — a full SSG rebuild has to run after deploy for those ~389 books to get generated.

Not addressed here, and separate: the catch-all `location /` returns 200 to bots for any non-SSG path (the bot-404 guard exists only in `@spa`), and Cloudflare's managed `robots.txt` block sets `Content-Signal: ai-input` absent plus `Disallow: /` for ClaudeBot/GPTBot/Google-Extended and friends, which is why Bing reports the site cannot appear in Copilot and grounding results. The latter is a product decision, not a bug.

## Users — entitlement tiers replace two hardcoded storage constants — backend — 2026-08-09

Triggered by a support case that turned out to be two unrelated ceilings wearing one error message. An upload failed with `Upload failed: 413` while the quota bar read 167.7 MB of 500 MB — plenty of room. **The 413 is Cloudflare's per-request body cap, not our quota**, verified against production by probing with increasing bodies: 10/50/90 MB reached the API (401 — the body got through), 110 MB returned `413 cloudflare`. nginx and Kestrel are both already configured at 500 MB and were never the constraint. That half is fixed separately by chunked upload; this entry is the other half.

The other half: storage limits were two `const`s on `User` (`StorageLimitBytes = 500MB`, `GuestStorageLimitBytes = 50MB`) read through a `user.IsGuest ? … : …` ternary duplicated at the two enforcement sites, and `IsGuest` was the **entire** user taxonomy — `User` has no role column, and `AdminUser` is a completely disjoint table with its own auth, own tokens and no foreign key to `User`. So "give the owner's account 5 GB" was not expressible at all, and neither was any future paid tier.

Introduces `UserTier { Guest, Free, Supporter, Staff }` as a **string** column (house style for new enum columns — readable in psql, immune to renumbering) plus a nullable `storage_limit_override_bytes` for genuine one-offs. Limits themselves live in the new `Entitlements` config section, not in code, so changing a quota is a config edit rather than a deploy: **Guest 50 MB · Free 500 MB · Supporter 2 GB · Staff 5 GB**. The options type deliberately mirrors `BudgetOptions` — root record with `Default` + a dictionary, static `Empty`, accessor-per-field normalizing its own "absent" sentinel, partial inheritance in `Lookup`, pure and never-throws — because that shape already solved this exact problem here and is unit-tested standalone. The binder is the same hand-rolled `AddSingleton` factory: an unknown tier key is skipped rather than thrown, so a typo degrades to the default instead of failing startup.

**The migration backfills `tier = 'Guest'` for existing guests.** The column default is `Free`, which is right for every registered account and wrong for guests — without the backfill, every existing guest would have silently jumped from a 50 MB to a 500 MB allowance the moment this deployed.

Three decisions worth recording. **Staff is granted by `Entitlements:StaffEmails`, not an admin endpoint** — there is no CRUD over site `User` anywhere in the admin app today, and building a management console for a population of one to three is the wrong trade; the config list is reviewable in git, needs no DB write and no new auth surface, and the column remains as a documented manual escape hatch. **The grant is fail-closed for guests**: if `IsGuest`, the allowlist is not consulted at all, because guest emails are synthesized (`guest-{guid}@guest.local`) and one collision must not be able to mint an anonymous 5 GB session. **`MaxSingleUploadBytes` lives on the root options record, not on `TierEntitlements`** — it is Cloudflare's ceiling, not a perk, so "Staff may upload bigger files" is *structurally* inexpressible (there is no key to put it under) and the binder additionally clamps it to a compiled-in platform constant. A test asserts guest and staff receive the identical value.

Two defects the tests caught in this change itself, both fixed. Staff-email normalization initially lived in the DI binder rather than in the options type, so a config entry with a trailing space or a capitalized domain would silently fail to match — and the failure mode (staff quietly not recognized) is invisible; a guarantee outside the type is not a guarantee, since tests and any other construction path bypass it, so it moved into the record. And `GetStorageQuotaAsync` initially kept a separate branch for "user not found", which could drift from what an upload actually enforces; both paths now go through the one resolver, so the quota endpoint cannot disagree with reality.

Also deleted rather than migrated: the `FileUpload:{MaxBookSizeMb,MaxCoverSizeMb,MaxPhotoSizeMb}` config block, which had **zero readers** while `MaxBookSizeMb: 100` read convincingly like the real limit.

`StorageQuotaDto` gains `Tier`, `MaxBooks`, `BooksUsed` and `MaxSingleUploadBytes` so clients can explain a refusal instead of surfacing a raw status code. **1379 unit tests green** (16 new in `EntitlementResolverTests`, covering the guest fail-closed rule, override clamping, and that a mistyped quota of `0` falls back to a working default rather than locking every user out of uploading). Build and `dotnet format --verify-no-changes` clean.

Not in this change: chunked upload (the actual 413 fix), any billing, and migrating the other per-user caps — vocabulary 5000, collections 50, tags 20, avatar 2 MB, agent cost caps — onto tiers. They are catalogued and deliberately left for later rather than folded into one PR with five new enforcement points.

## Worker — provider readiness check + circuit breaker, and a Sentry environment tag that lied — backend + infra — 2026-08-08

**First, a correction, because this entry exists because of a misread and repeating it would be worse than the bug.** The Sentry issue that prompted this work (`System.Net.Http.HttpRequestException: Name or service not known (ollama:11434)`, 30 events, tagged `environment: Production`) did **not** come from production. It came from a developer machine. Four independent checks: the events report `linux-arm64` (prod is x86_64), release `ee15354c` (a branch commit that was never deployed — prod went `71c6b1da` → `df551f15` → `bb7cfc1c` → `58fec417`), prod's `ollama` container has been `Up 4 weeks (healthy)` with the Worker resolving it to `172.18.0.8`, prod's Worker logged **zero** occurrences of "ollama" in 24 h, and prod has **zero** backfill candidates (`status = Ready AND genre IS NULL`) — every one of its 50 user books has a genre. The "38 starved books" were a local database.

**Why the tag lied, and the fix.** The local `.env` sets `ASPNETCORE_ENVIRONMENT=Production`, so a dev box pointed at the production DSN wrote events into the production Sentry project under a production tag. Anyone reading that UI would conclude "prod", and someone did. `SentryBootstrap.ResolveEnvironmentName` now downgrades a `Production` claim to **`production-unverified`** when `SENTRY_RELEASE` is absent — the release is set from the `GIT_SHA` build arg in both Dockerfiles, so every CI-built image has one and no `dotnet run` ever does. Real production is unaffected. Deliberately a rename rather than a drop: an unverified event is still worth having, it just must not masquerade (filter with `!environment:production-unverified`). `.env.example` gained a warning, and the local `.env` was corrected.

**The hardening stands on its own merits, which are not hypothetical.** Nothing checked provider reachability at startup, so a genuinely dead prod Ollama would fail exactly as silently — `distractor`, `bookmeta`, `tagsuggestion` and every unrouted tag (the Worker's `Ai:DefaultProvider` is `ollama`) degrade quietly. `MetadataBackfillWorker` would spend up to **50 × `Ollama:TimeoutSeconds` (90 s) ≈ 77 minutes** of dead wall-clock per worker start. And worst: `UserBookEnrichmentService.EnrichAsync` stamps **`Completed`, not `Failed`,** when the generator returns null — which is exactly what an unreachable provider produces — so `MetadataEnrichmentWorker`'s 30 s drain would quietly empty the queue into a terminal "done, nothing filled" state that nothing revisits. That last one is provider-independent data loss and was worth the trip on its own.

**What shipped.** `AiProviderReadinessCheck` (replacing `EnrichmentKeyCheck`, whose job it strictly supersedes and whose hardcoded provider set had already drifted — it omitted `openai-pdf`, the most expensive route in the system) probes every provider the route table actually references, once, before any worker loop starts: Ollama via `GET {Ollama:BaseUrl}/api/tags` on a 2 s timeout (the same probe shape the API's `/health/ready` already uses), OpenAI-family by key presence only — **it never spends a token to prove a paid provider is up**. An unreachable provider produces one `LogError` naming the affected tags (`(default), bookmeta, distractor, tagsuggestion → ollama (unreachable)`) plus one Sentry warning, and seeds that provider's circuit open. It can never crash or block the host.

`ProviderCircuitPolicy` is the breaker: pure statics with the clock as a parameter, mirroring `AlarmThrottle` because this repo has no clock abstraction. `OpenedAt` survives escalation, so `JustTripped` is true exactly once per outage — **that single predicate is the whole "one event per condition, not one per retry" requirement**, and it is what turns 30 duplicate events into 1. Backoff 1 → 5 → 30 min (`Ai:ProviderHealth:BackoffMinutes`). Detection lives **inside `OllamaLlmClient`**, beside the three existing `LlmFailureAlarm.Capture` calls, because that is the only place that knows a call died on the wire: the client swallows transport failures and returns an empty response, so a decorator would see success-with-empty and could not distinguish a dead Ollama from a model that said nothing. A **non-2xx deliberately does not trip** — that means Ollama is alive and answering (typically a wrong `Ollama:Model` → 404), fails in milliseconds, and hiding it behind 30 minutes of silence would turn a cheap visible error into an invisible one.

**No silent fallback, in either direction.** Nothing here can move a task to a different provider; `ModelGateway.cs` is not modified at all. Rerouting an outage onto a paid provider is the 2026-07-14 390%-CPU incident with the arrow reversed. Provider choice stays 100% `Ai:Routes`-driven, and the Worker config now states prod intent explicitly instead of implying it.

**Verified against the real failure, not a mock**: local Ollama down, Worker started with `SENTRY_DSN` unset. Before, the backfill would make 38 calls; after, the log reads `enriching 38 user books` → `aborting after 0 enriched / 1 failed — provider 'ollama' is unavailable; the remaining candidates stay queued`, and exactly **one** HTTP request reached the wire (the half-open probe). The 38 candidate rows were still queued afterwards. That per-book re-check was added *because* the first live run exposed the gap: the startup probe opens the circuit on a 1-minute rung while the backfill only wakes at its 2-minute start delay, so the circuit is legitimately half-open by then and a single up-front gate let the whole batch begin. **1363 unit tests green** (79 new across `ProviderCircuitPolicyTests`, `ProviderHealthRegistryTests`, `AiRouteMapTests`, `AiProviderReadinessCheckTests`, `OllamaCircuitBreakerTests`, `MetadataWorkerGateTests`, `SentryEnvironmentTests`), including "20 concurrent callers at `RetryAt` yield exactly one probe" and "30 consecutive failures alarm once". Build + `dotnet format --verify-no-changes` clean. No migration. `Ai:ProviderHealth:Enabled=false` is a kill switch restoring byte-for-byte the previous behaviour.

Both new Sentry events carry explicit fingerprints keyed only on (event kind, provider) — without them `CaptureMessage` groups on the rendered message, which contains the volatile task list and retry duration, so every route edit would spawn a fresh issue and "resolved in release" would never stick.

## Observability — Sentry leaked SQL a second way: EF Core error EVENTS, not just breadcrumbs — backend — 2026-08-07

> Postmortem: [`docs/incidents/2026-08-07-sentry-scrubber-leaked-sql.md`](../incidents/2026-08-07-sentry-scrubber-leaked-sql.md)

Caught by the integration's own first day in production. Yesterday's PR (#445) found and fixed EF Core **breadcrumbs** carrying `Executed DbCommand … SELECT …` in their message; that fix was real but incomplete. EF Core also logs a *failed* command at **Error** level, and Sentry's `ILogger` integration turns any Error into an **event** — so the first live capture of the (separately real) `PUT /me/progress` failure arrived with `INSERT INTO reading_progresses (id, chapter_id, edition_id, locator, max_chapter_number, percent, site_id, updated_at, user_id) VALUES (@p0, …)` inline in the event message. Two distinct channels, one shared assumption: that nulling the structured `data` bag was where the SQL lived. It never was — EF interpolates the statement into the human-readable text on both paths.

Scope of the exposure, stated precisely: **no parameter values ever left the process** — `EnableSensitiveDataLogging` is off, so EF renders `@p0` / `'?'`, and Npgsql itself writes "Detail redacted as it may contain sensitive data" on the inner `PostgresException`. What did leave was statement shape and schema (table and column names). No book text, no reader identity. Still a promise this integration explicitly made and broke, and schema disclosure to a third party is not free.

Fix: `SentryScrubber.Scrub` now drops any event whose `Logger` starts with `Microsoft.EntityFrameworkCore`, plus a message probe for `Executed DbCommand` / `Failed executing DbCommand` so a re-categorised logger can't reopen the hole (`SentryScrubber.IsDatabaseCommandEvent`). **Dropping loses no signal**, which is what makes it the right call rather than a redaction exercise: the same failure is already reported by `ExceptionMiddleware` as a `DbUpdateException` carrying a full stack trace, the Npgsql SQLSTATE (`23505`) and the violated constraint name — everything needed to debug it, none of the SQL. A test locks that the middleware event survives while the EF command event dies.

The generalisable lesson, and the reason this is worth a CHANGELOG entry rather than a quiet patch: **a scrubber written against one egress path will be bypassed by the next one.** The original design rejected Sentry's OpenTelemetry exporter precisely because it bypasses `BeforeSend` — then shipped with two log-pipeline channels doing the same thing from the inside. Unit tests were green throughout both, because they asserted the scrubber's behaviour on the input shape we imagined rather than on what the SDK actually assembles. Only reading a real captured event found either one.

**1284 unit tests green** (3 new), build + `dotnet format --verify-no-changes` clean. No migration, no config, no behaviour change when `SENTRY_DSN` is unset.

<a id="2026-08-07-reader-reading-position-was-silently-lost-on-concurrent-save"></a>

## Reader — reading position was silently lost on concurrent saves (23505 upsert race) — backend — 2026-08-07

> Postmortem: [`docs/incidents/2026-08-07-reading-position-lost-23505.md`](../incidents/2026-08-07-reading-position-lost-23505.md)

Found by Sentry on its first day in production, which is the point of having installed it. `PUT /me/progress/{editionId}` was throwing `Npgsql.PostgresException: 23505: duplicate key value violates unique constraint "ix_reading_progresses_user_id_site_id_edition_id"` — ten times in four hours, from real readers, returning a 500 and **dropping the reader's position in the book**. Nothing crashed, no test failed, and the only prior symptom would have been a user saying "it forgot where I was".

Root cause is a textbook read-then-insert with no concurrency control: `UpsertProgress` queries `ReadingProgresses` for the row, and inserts when it finds none. One reader legitimately produces overlapping writes — the 30s session heartbeat, a `sendBeacon` on unload, an offline-queue flush after reconnect, or simply a second device — so two requests both see no row, both `INSERT`, and the loser violates the unique index. The window is milliseconds wide, which is why it only appears at real traffic and never in a test.

Fix: catch the unique violation and merge into the winner's row instead of failing. On `DbUpdateException` with SQLSTATE **23505** (matched via `PostgresErrorCodes.UniqueViolation`, not a message string, so it survives locale and constraint renames) the doomed insert is detached, the winner is re-read, and the client's write is applied to it — the exact update path we would have taken had we lost the race by one more millisecond. Critically, **the stale-write guard is re-applied against the WINNER's timestamp**, so recovering from the race still cannot move a reader backwards; and the monotonic `MaxChapterNumber` high-water mark (which feeds the RAG spoiler gate) is raised through the same shared `ApplyProgressUpdate` helper used by the normal path, so the two can never drift. A unique violation with no winning row (e.g. deleted in between) is rethrown rather than silently swallowed — that is not the race we know how to recover from.

Chosen over a native `INSERT … ON CONFLICT DO UPDATE` deliberately: the endpoint's semantics include an early return that echoes the *existing* row back when the client's timestamp is stale, which does not express cleanly in an upsert statement, and rewriting a hot path into raw SQL to fix a millisecond race is more risk than the race. The retry keeps every existing behaviour and touches one method.

**1289 unit tests green** (9 new, locking the high-water-mark monotonicity, the NULL-vs-ordinal-0 seeding rule, and that the recovery triggers on 23505 and nothing else — a foreign-key violation must still surface). Build + `dotnet format --verify-no-changes` clean. No migration.

<a id="2026-08-06-observability-sentry-for-api-worker-with-llm-agent-and-provi"></a>

## Observability — Sentry for API + Worker, with LLM agent and provider-routing spans — backend + infra — 2026-08-06

TextStack had **no error tracking at all**. OpenTelemetry has been wired since feat-0005, but it exports to an `aspire-dashboard` container that is profile-gated **off in production** — so for the whole life of the AI stack, prod telemetry has been going nowhere and nobody was alerted on anything. The trigger for fixing it was the 2026-07-14 incident (entry below): the Worker's `Ai:Routes` had no `pdf.parse` entry, so the user-PDF vision parse fell through to `Ai:DefaultProvider: ollama` and pegged the CPU-only Ollama container at **~390% for ~42 s/page across a 106-page book**. Nothing threw, nothing logged an error, no OpenAI traffic appeared, and the job simply produced zero chunks. **The failure mode was silence, and silence is exactly what a monitoring stack has to be taught to notice.** A reader of the write-up suggested emitting the resolved provider as a span attribute; that suggestion is the core of this change.

**The routing spans.** `ModelGateway.Route` and `ModelGateway.ResolvedPrimaryKey` each independently recomputed the same precedence — registry Primary → `Ai:Routes:{feature}` → `Ai:DefaultProvider` → literal `"openai"` — and neither could tell a *deliberate* route from a *silent* fallback, because the whole thing was one `??` chain that collapsed both into a string. Both now go through a single `ResolveRoute()` returning `(Key, Reason)`; the key expression is unchanged, so the resolved provider is provably identical (locked by a precedence theory in `ModelGatewayRouteReasonTests`). Every gateway call now attaches `ai.task`, `ai.provider.resolved` and `ai.provider.reason` (`route_matched` | `default_fallback`) to the ambient span — on the Sentry span *and* the OTel `Activity`, so the answer to "which model actually served this, and did anyone choose it on purpose?" comes from a trace instead of from a CPU graph. On top of that, an **expensive** task landing on `default_fallback` raises a Sentry warning outright: falling back to the default is normal and correct for most features, but for `pdf.parse`, `rag.summarize` and `podcast.script` (config `Ai:RouteAlarm:AlertOnDefaultRouteFor`) it is a defect by definition. **Throttling is load-bearing, not polish**: `pdf.parse` resolves once per page with parallelism 6, so that 106-page book would have raised 106 identical events — `AlarmThrottle` dedupes per `(task, provider, reason)` on a 60-minute cooldown (`Ai:RouteAlarm:CooldownMinutes`) while still firing the *first* hit immediately, so a bad deploy is visible within one page.

**Agent + RAG spans.** `AgentLoop.StreamAsync` is the single seam every agent runs through — Enrichment, Librarian, Tutor, StudyBuddy and the crews — because `RunAsync` is pure delegation, so one `using var trace = TraceScope.Start("agent.run", "ai.agent")` covers all of them (`using` is legal in an iterator and disposes on completion, `yield break`, throw *and* consumer abandonment). Each run reports `agent.name` (the `FeatureTag`, which is both the agent identity and the key `Ai:Routes` is indexed by, so the tag joins with routing config), `agent.model`, and measures for iterations/tokens-in/tokens-out/cost/duration; the outcome defaults to `error` and is set to `completed` or `budget_exhausted` at the three terminal paths, mapping 1:1 onto `AgentRunRecordFactory`'s statuses. `RagIndexingService` opens a `rag.index` span per book **after** the atomic claim (a lost claim is the common no-op and emits nothing) carrying `rag.kind`, `rag.book_id` and `rag.chunk_count`, and both `FailUserBookAsync`/`FailEditionAsync` — the single choke point for `rag_status = 3` — now raise a Sentry error carrying the `rag_error`. One deliberate exception: **`"indexing interrupted, retry"` is never sent**, because it fires on every deploy that lands mid-index and the sweep re-queues it — paging on a self-healing state on every release is how alerting dies.

**Provider failures.** `OllamaLlmClient` swallows non-2xx, timeouts and transport errors and returns an empty zero-token response — which is load-bearing (callers depend on it), and is precisely why those failures are invisible in `llm_traces`: `TracingDecorator` only ever sees a successful, empty answer. The swallow is untouched; each of the three branches now also calls `LlmFailureAlarm.Capture` with `ai.provider` / `ai.task` / `ai.failure` tags, on the same throttle. OpenAI failures need no such handling — they propagate to `TracingDecorator`'s two non-cancellation catches, the single choke point, which now reports them with the provider key (threaded in as a trailing optional ctor param so no existing test construction churned). Cancellation stays excluded on both paths: an SSE client disconnecting is not a model error.

**Why not `Sentry.OpenTelemetry`.** The obvious move — bridge the existing OTel spans into Sentry so there is one instrumentation — was rejected on evidence. Sentry deprecated that package, and its replacement (`Sentry.OpenTelemetry.Exporter`, on beta OTLP ingest) ships spans through the *OpenTelemetry* SDK, meaning `BeforeSend` never sees them. Our OTel spans carry `http.client_ip` (`ServiceCollectionExtensions.Hosting.cs`) and full SQL text (`SetDbStatementForText = true`), and there is no hook to strip either on the way out — that is a hard blocker for a reading app. It would also have forced Sentry's sample rate onto the shared `TracerProvider`, coupling the cost knob to the Aspire pipeline. Instead `TraceScope` dual-writes: one `Activity` (→ OTLP/Aspire, one added `AddSource` line is the *only* change to the existing pipeline) and one Sentry span (→ scrubbed at the edge).

**Noise and privacy.** `SentryScrubber` is an **allowlist, not a denylist** — every tag and extra not explicitly blessed is dropped or redacted. A denylist only stops the leaks someone remembered to enumerate; with an allowlist a future `span.SetTag("prompt", userText)` dies at the edge whether or not a reviewer caught it. On top of that: `SendDefaultPii = false`, `MaxRequestBodySize = None` (uploads are books, POST bodies are reader prompts), user identity blanked, `Authorization`/`Cookie`/`X-Admin-*` headers stripped, free text run through the existing `TraceRedactor` and truncated to 512 chars, breadcrumb `data` bags dropped wholesale, and `/health` + `/health/ready` sampled at 0.0. Client-error exceptions (`NotFoundException`, `ConflictException`, `ValidationException`, `DomainException`, `BudgetExceededException`, cancellation) are dropped — none can reach Sentry today because `ExceptionMiddleware` maps them to 4xx *without logging*, but the filter guards a future `LogError` on a validation path. Rate-limiter 429s are not exceptions and were never in scope. Sampling is deliberately asymmetric: `http.server` at `Sentry:TracesSampleRate` (0.2 prod, 1.0 dev), but `ai.agent` and `rag.index` **always at 1.0** — they are rare and they are the entire reason for this integration; sampling them at 0.2 would discard four of every five traces we added Sentry to see.

**Wiring and the no-op guarantee.** API takes `Sentry.AspNetCore` (6.8.0 ships a first-class `net10.0` TFM with zero dependencies); the Worker is a generic host with no request pipeline, so Sentry rides the ILogger provider — additive, the OTLP logging provider is untouched. Both call sites **skip the SDK entirely when `SENTRY_DSN` is empty** rather than initialising with a blank DSN (which still installs middleware and logs a startup diagnostic), so local dev, CI and forks are byte-identical to before. All the seam code (`SentrySdk.CaptureMessage`, `GetSpan`) is already inert against a disabled hub, so no `if (enabled)` guards leaked into `AgentLoop`, `ModelGateway` or `RagIndexingService`. `MinimumEventLevel = Error` is what actually captures unhandled errors: `ExceptionMiddleware` catches everything and returns a 500, so nothing ever reaches Sentry's own middleware — errors arrive via its `logger.LogError(ex, "Unhandled exception")`, confirmed in the verification below (the captured event's `logger` tag reads `Api.Middleware.ExceptionMiddleware`, `mechanism: SentryLogger`). Release plumbing is six lines of infra and no C#: `ARG GIT_SHA` → `ENV SENTRY_RELEASE` in both Dockerfiles (declared after the publish copy so a new SHA invalidates only that trivial layer, not the .NET build or the ~150 MB puppeteer install), `build.args` in compose, and `export GIT_SHA=$(git rev-parse --short HEAD)` in `deploy.yml` — `.dockerignore` excludes `.git`, so the build arg is the only way the SHA can get in, and without a release Sentry cannot do regression detection or tell you which deploy an issue started with.

**Verified end-to-end against the real DSN**, not just unit-tested: `POST /admin/diagnostics/sentry-test` (admin-gated by the existing path-based middleware; 401 unauthenticated) returned `{"eventId":"68aa5de7…","enabled":true}` and the API logged the same id; `POST /admin/diagnostics/sentry-test-error` returned 500 and produced a Sentry issue tagged **release `71c6b1da`, environment `Production`**, with `logger: Api.Middleware.ExceptionMiddleware` and only `Accept`/`Host`/`User-Agent` in the request headers — **the admin session cookie the request carried is absent**, user is empty, no body. A synthetic routing event confirmed the allowlist on the wire: `ai.task=pdf.parse`, `ai.provider.resolved=ollama`, `ai.provider.reason=default_fallback` survived; a `prompt` tag was **gone** and a `response` extra came through as `[redacted]`; an exception message containing an email arrived as `TextStack verify: synthetic failure for [redacted-email]`. One honest caveat: Sentry still shows a coarse **Geography (city-level)** derived server-side from the ingest connection IP — that is inferred at their edge, not sent in our payload, and in production it resolves to the datacenter rather than a reader. **1281 unit tests green** (35 new across `SentryBootstrapTests`, `SentryScrubberTests`, `AlarmThrottleTests`, `ModelGatewayRouteReasonTests` — including `TryEnter_RepeatedWithinCooldown_ClaimsOnce`, which replays 106 page-parallel calls and asserts exactly one event), `dotnet build` and `dotnet format --verify-no-changes` clean. No migration. No changes to web or mobile.

**Two findings from running it for real, both fixed/known before merge.** First, the scrubber leaked SQL. Pointing the local Worker at the branch build surfaced a genuine failure — the Ollama container wasn't running, so `MetadataBackfillWorker` threw 38 transport errors — and the resulting Sentry event's **breadcrumb trail carried `Executed DbCommand … SELECT m.feature_tag … FROM models`**. EF Core puts the SQL in the breadcrumb *message*, so nulling the structured `data` bag did nothing; this is the same `SetDbStatementForText` class of leak the PR avoided by rejecting Sentry's OTel exporter, quietly re-entering through the log pipeline. Fix: `ScrubBreadcrumb` now **drops EF Core command breadcrumbs entirely** (by category or by an `Executed DbCommand` message probe) rather than redacting them — a diagnostic breadcrumb is not worth shipping query text about what people are reading to a third party. Re-verified on a fresh live event: no `DbCommand`, no SQL. Second: those same 38 failures produced **exactly one Sentry event**, tagged `ai.provider=ollama`, `ai.task=bookmeta`, `ai.failure=transport` — the throttle working against a real running process rather than a unit test, and a failure mode that produced zero visibility before this PR. **To be exact about provenance, because the event itself is not:** this was a developer machine, not production — prod's `ollama` service was healthy throughout. The event nevertheless arrived tagged `environment: Production`, because the local `.env` sets `ASPNETCORE_ENVIRONMENT=Production`. That mislabelling is a real defect in its own right (a dev box writing into the production Sentry project under a production tag) and is fixed separately; it is called out here so nobody later reads this entry as a production incident.

**What we expect it to catch first**, in order of likelihood: a `default_fallback` on `rag.summarize` or `podcast.script` in the Worker (the same class of config drift as the original incident, now audible); Ollama timeouts during vocabulary distractor generation, which are today completely invisible because the client swallows them; and terminal RAG indexing failures on user PDFs, which until now surfaced only as a book stuck on a badge in the UI.

**Owner step:** `SENTRY_DSN` must be added to the prod `.env` by hand before the first deploy that ships this — deploys go through GitHub Actions and the server `.env` is not managed by them. Until it is set, Sentry stays off in production, which is the designed safe outcome.

## RAG — deterministic tie-breaker on retrieval ORDER BY (repo now matches the article) — backend — 2026-07-15

RAG stays the differentiator ChatGPT can't match — answers grounded in *your* file with citations that jump to the page. Deferred (noted): precomputed per-chapter summaries at index time (the real fix for whole-chapter summaries) and a gpt-5-mini shadow-route comparison via the RLOps infra. `dotnet build` + **1172 unit + 77 AiEvals** green (grounding/citation evals unchanged — the register change didn't regress them); web `tsc`/`vite build` + **714** vitest. <a id="2026-07-14-reliability-a-slow-hung-rag-parse-can-no-longer-wedge-the-in"></a>

## Reliability — a slow/hung RAG parse can no longer wedge the indexing worker — backend — 2026-07-14

> Postmortem: [`docs/incidents/2026-07-14-rag-parse-wedged-worker.md`](../incidents/2026-07-14-rag-parse-wedged-worker.md)

Follow-up to the durable-indexing work: the sweep loop `await`ed each book's chunk (vision parse) **inline**, so one slow or hung parse blocked the whole loop — no drain, and critically no stale-reclaim — until it returned. The mis-routed 74-minute Ollama parse wedged the worker exactly this way. Now the sweep **detaches** the parse to a background `Task.Run` gated by a `SemaphoreSlim(1)`: it dispatches at most one parse at a time (bounds paid vision spend) and the loop keeps running stale-reclaim + drain checks every 30 s, so a stuck parse can't wedge it. A **hard parse timeout** (`Ai:Pdf:ParseTimeoutMinutes`, default 12, clamped below the 15-min stale window) terminates a live-but-slow parse to `Failed`/"indexing timed out, retry" before the stale sweep would — and the render phase now honors the token too, not just the vision calls. Restart-safe (the atomic `rag_indexing_started_at` claim runs before the parse, so a killed detached task is recovered by the stale sweep). **Hardened by adversarial QA** — the review caught (and this fixes) a **HIGH** semaphore leak: a DB exception between `Wait(0)` and dispatch would have leaked the slot permanently → the very silent-worker-wedge the change set out to kill; now a `try/finally` releases the slot on every non-dispatched path. `dotnet build` + **1120 unit** tests green. Live parse verified on prod earlier (OSCE: 375 chunks → Ready in ~4 min on gpt-4.1); the detach/timeout paths are unit-tested where pure and reasoned through for concurrency (no local OpenAI key / arm64 SIGILL).

## Hotfix — PDF vision-RAG parse routes to gpt-4.1 in the Worker (was Ollama) — 2026-07-14

> Postmortem: [`docs/incidents/2026-07-14-pdf-parse-fell-to-ollama.md`](../incidents/2026-07-14-pdf-parse-fell-to-ollama.md)

Regression from the durable-indexing change (which moved chunking off the API request into the Worker): the Worker's `Ai:Routes` had **no `pdf.parse` entry**, so the user-PDF vision→Markdown parse fell through to the Worker's `DefaultProvider: ollama` instead of `gpt-4.1`. ## Reliability — "Ask this book" indexing no longer gets stuck + reading sessions survive a deleted book — backend + web — 2026-07-14

Two prod-confirmed reliability holes. **"Ask this book" could stick on "Preparing… 0/0" forever.** `POST /me/books/{id}/index` (and the catalog twin) atomically claimed `NotIndexed/Failed → Indexing`, then ran the chunking — for a PDF the **minutes-long `PdfVisionParser` vision parse** — **synchronously inside the HTTP request**, only returning `202` once it finished. When that request died (Cloudflare ~60-100s timeout, or the API container restarting on deploy — which is exactly how the OSCE workbook got stuck), the row was left `Indexing` with 0 chunks and **no terminal `Failed`**; the claim only re-claims from `NotIndexed/Failed`, so `Indexing` was a permanent dead end. Fixed by moving chunking **off the HTTP path into the Worker**, mirroring the enrichment-reliability pattern: the endpoint claims and returns `202 Indexing` immediately; a `RagIndexingService` executor does the work under an atomic `rag_indexing_started_at` claim and **always reaches a terminal state** (`chunkCount==0` / exception / cancellation → `Failed`); a `RagIndexingWorker` sweep (30s, one book/cycle to bound paid vision spend) drains queued books and reclaims dead-process `Indexing` rows (`started_at` older than 15 min) → `Failed`. The `ChapterEmbeddingWorker` chunk→embed→`Ready` hand-off is unchanged; catalog and user-book paths unify on the one executor. Migration adds nullable `rag_indexing_started_at` (+ partial sweep indexes) on `user_books` + `editions`. **Hardened by adversarial QA**: the embedder now marks a book `Failed` when it permanently poisons a chunk (previously `embedded < chunk_count` stranded it `Indexing` forever, bypassing the `chunk_count=0` sweep); the executor's chunk-count stamp is a guarded `WHERE rag_status=1` UPDATE (a stale-swept `Failed` row can't be clobbered); `embedded_count` is recomputed from actual rows after chunking (was a blind `0`, losing an embedder-drains-first race); and cancellation writes "indexing interrupted, retry" instead of a misleading "no chapters". Known follow-up (accepted): full concurrency/detach for a multi-Worker deployment (the model assumes a single Worker today).

Separately, **reading sessions for a deleted book stopped flooding 500s.** After re-uploading a book (old id gone), the client's queued/`sendBeacon` sessions kept resubmitting for the dead `user_book_id`, hitting a Postgres `23503` FK violation → unhandled `DbUpdateException` → 500, retried forever. Now `ReadingSessionService.SubmitAsync` existence-checks the referenced book (owned + live user book, or a real edition) and returns **404** for a gone book (with a belt-and-suspenders `23503` catch → benign ack), and the client **prunes** the queued session on a 404 instead of re-queuing it (5xx/network still retry). `dotnet build` + **1113 unit** tests (+ session/RAG integration tests: `202 Indexing`-without-chunking, session `404`); web `tsc`/`vite build` + **684 web** vitest. The live chunk→embed→`Ready` round-trip verifies on prod (arm64 worker SIGILL + no local OpenAI key); already-stuck prod rows are cleared by a one-off backfill at deploy.

## Ops — root cause: the nightly backup was leaking 156 GB of orphaned pgdata volumes — infra — 2026-07-10

> Postmortem: [`docs/incidents/2026-07-10-backup-leaked-156gb.md`](../incidents/2026-07-10-backup-leaked-156gb.md)

The actual root cause behind the flapping backup (the self-diagnostics below were added to *find* this). Prod's Docker data-root lives on a **separate `/mnt/data` partition** (not `/`, which `df -h /` alone hides) and it had hit **100% / 0 bytes free** — 183 GB used, **156 GB of it 57 dangling anonymous `pgdata` volumes**. `backup-verify.sh` spins a throwaway `pgvector` postgres each run; postgres declares an anonymous `VOLUME /var/lib/postgresql/data`. On a killed/timed-out run `--rm` never fired and the cleanup did `docker rm -f` **without `-v`** → one full pgdata volume leaked per run. 34 days × daily ≈ 156 GB → the docker root filled → a fresh throwaway postgres could no longer `initdb` → **the backup broke the very verify step that had been creating the volumes** — a self-reinforcing failure. Real prod data was never at risk (postgres + storage bind-mount to `/`, which was at 61%); only the anonymous verify volumes bloated `/mnt/data`. Fix: `docker rm -f` → **`docker rm -fv`** (both the trap cleanup and the leaked-container reap) so the anonymous volume dies with its container, plus a `docker volume prune -f` catch-all for SIGKILL'd runs the trap can't cover (named volumes are untouched by prune). Remediated live: `docker volume prune` reclaimed **163 GB**, `/mnt/data` 100% → 17%. Diagnosed the hard way — the box was also unreachable for a stretch (a clean manual reboot, not a crash; a full disk still lets you SSH in, so an SSH *connect*-timeout is a host-offline signal, not disk).

## Ops — backup verify self-diagnoses failures + reaps leaked containers — infra — 2026-07-10

The daily backup's restore-verify step (`infra/scripts/backup-verify.sh`, which restores the dump into a throwaway pgvector container) was failing with a bare `postgres did not become ready` that hid the real cause. <a id="2026-07-09-auth-fix-spurious-unauthorized-mid-session-refresh-token-sta"></a>

## Auth — fix spurious "Unauthorized" mid-session (refresh-token stampede) — web — 2026-07-09

> Postmortem: [`docs/incidents/2026-07-09-refresh-token-stampede.md`](../incidents/2026-07-09-refresh-token-stampede.md)

Fixed the reader dead-ending on **"Error loading chapter — Unauthorized"** after ~an hour, even though the user was still signed in (Google/email). Root cause: the access token expires at 60 min, and the reader fires many authenticated requests in parallel (chapter, book, progress, bookmarks…), so they all 401 at the same instant and each independently called `/auth/refresh`. The server **rotates** the refresh token on every refresh (deletes the presented token, issues a new one), so only the first concurrent refresh won — the rest presented the now-deleted token and got 401, surfacing as a spurious mid-session logout. Fix: `refreshToken()` in `apps/web/src/api/auth.ts` is now **single-flight** — concurrent callers share one in-flight `/auth/refresh`, so there's exactly one rotation and one fresh cookie, then every caller retries. This makes silent refresh reliable, so an active user stays signed in across the full rotating refresh-token window (i.e. until they explicitly log out or are inactive past the TTL) instead of being bounced hourly. Pure client change, no backend/token-config change. `tsc` clean, `vite build` green, **22 auth/api vitest** green (3 new: concurrent-dedup, fresh-request-after-settle, lock-clears-on-failure). Mobile (`apps/mobile/src/lib/api.ts`) already single-flights refresh — not affected.
