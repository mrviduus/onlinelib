## Reader — a restore now says when it has landed, and nothing is saved before it does — mobile — 2026-08-29

QA opened a book at 45%, pressed back inside a second, and the stored position was 0.66%. Twice, on both entry points, with the loss scaling to how far in the reader had got — 45.2% and 40.3% both collapsed to 0.66%, while 11% dropped 1.5 points at a time and kept dropping on each repeat. A normal fifteen-second visit drifted 21px, so the damage was specific to leaving early.

**The gate added the day before was guarding the wrong instant.** `#497` made the mobile reflow reader refuse to write a position until one had been restored, and set that flag in `tryRestore` — the function that *injects* `window.__textstackRestoreScroll` into the WebView. Injection is not arrival. The scroll happens a paint later in another JavaScript realm, and until it reports back, the newest position React Native holds is the `scrollY: 0` the page posts on its own `load` event. The gate was wide open across that entire window, so the unmount flush, the background flush and the debounce all had a zero to write. The restore functions were fire-and-forget and returned nothing; the only feedback was the scroll event they caused, which arrives as an ordinary `progress` message indistinguishable from the reader scrolling and is suppressed outright when the delta is under 0.005. There was nothing to wait for.

So the restore now acknowledges itself. Each one carries an id into the WebView and reports back under its own `restored` message with the offset it reached — the same shape the PDF viewer has used since `pdfPersistGate`, which was written after this same class of bug on the other reader: `scrollToPage(page, jumpId)` in, `ackJumpId` out. The two-state predicate becomes a three-phase machine, `awaiting → issued → open`, and `issued` is the state that did not exist before. It has three ways out, and each earns its place: an id-matched acknowledgement (the happy path, and the id is what stops an ack from the chapter just left opening the gate on the chapter just entered); any reported position above zero, which stands in for a lost acknowledgement because wherever the reader is, they are somewhere real — the load event's zero, deliberately, opens nothing; and a four-second settle timeout on a real timer, the same value and the same argument as `PDF_JUMP_SETTLE_MS`, because one injection that never arrives must not silence saving for the rest of the session. Losing the tail of one session is bad; losing every session is worse. "Nothing was saved" still opens the gate immediately — the top of the chapter is where that reader belongs, and treating it otherwise would mean a first read could never be persisted at all.

The percent branch got a function of its own while the ack was being added. It had been a raw string injected from the hook with no counterpart in the page, which is precisely why it had nowhere to report from; both branches now go through the same helper and the same acknowledgement, and the settings-rebuild re-apply reuses it too. One incidental trap worth recording: the reader document is a single TypeScript template literal, so a backtick in a comment inside it ends the string — the first version of this change did exactly that, and `tsc` reported it as a module declaration error two lines away from the real cause.

Not fixed, deliberately: the report also notes ~75px lost on each re-entry, about 0.05% a time. The likely cause is `scrollTo` under-shooting before the document height has settled — the PDF path handles it by checking page dimensions before acking — but a re-application loop is a new source of races bought for a twentieth of a percent. The acknowledgement now carries the achieved offset, so it is at least measurable when it matters.

## Mobile — the language question is decided while rendering, not by an effect that could be missed — mobile — 2026-08-28

Third reproduction, third fix. A brand-new account on a cleared install lands on Library with no language question; `GET /me/profile` says `nativeLanguage: null`, so asking was required; the question then appears on the next cold start. Identical to the two runs before it. **The reason three attempts produced no diagnosis is mine:** the instrumentation written to settle it — three `console.log` calls added in #474 — sits behind `__DEV__`, and every reproduction ran a release build from Play plus an OTA, where `__DEV__` is false. A question that could not answer itself, asked three times. Worse, one of the two plausible mechanisms was also mine: `router.dismissAll()` before `replace()` was added in #474, i.e. after the second reproduction, and expo-router queues both, computing the REPLACE against a route tree that has not yet absorbed the POP_TO_TOP dispatched in the same drain. So the shape changes rather than the guess. The gate was a null-rendering sibling of the root `<Stack>` deciding inside a `useEffect` with two early returns, one of which tested a `pathname` that is stale at exactly the moment registration navigates. It is now a decision taken during render, in the tabs layout, where the reader actually lands — `<Redirect>` when the answer is "ask", the tabs when it is not, and the tabs while it is still unknown. A render-time decision cannot be skipped the way an effect can, and it has to live inside a screen subtree because expo-router's `<Redirect>` is built on `useFocusEffect`, which needs a focus context a sibling of the navigator does not have. The `alreadyOnboarding` guard became structural: the onboarding route is outside the tabs, so the layout is not mounted while it shows. `landAfterAuth` keeps one job — leave the auth modal — because two copies of the rule is how it drifted. Evidence now survives a release build: a Sentry breadcrumb records the five inputs and the answer, so a fourth reproduction would finally leave a trace. Found while tracing and fixed alongside, because it is not an onboarding bug at all: `useReaderVocabActions` still held `nativeLanguage !== language ? nativeLanguage : 'en'` — the exact fallback `useTargetLanguage` was rewritten to delete — so saving a word from an English book with no native language set produced the card `lucius → Lucius`. A word with nothing to translate into is now saved as it is.

## Mobile — a book screen re-reads where you got to, instead of showing where you were before you read — mobile — 2026-08-28

Read a PDF to page 24, press back, and the book screen showed a dash where the percentage goes, a greyed-out progress bar, and a button saying "Start Reading" — while the server already held `{"locator":"page:24","percent":0.197}`. Leaving the screen and returning fixed it. Three symptoms, one cause: `savedProgress` was still the `null` it was initialised with, because the reader is opened with `push` and left with `router.back()`, so the book screen is never unmounted, and its load effect is keyed on `[id, reconnects, attempt]` — none of which change when a reading session ends. It is the first thing you see on closing a book, so it is not a defect anyone can miss. The fix is the pattern the repo already had and had already written the rationale for: `useContinueReadingList` recomputes on focus, noting that "the only thing that changes these values is the user leaving the reader, which is a focus event". Only the progress is re-fetched — a book's own fields do not change by reading it — and a failed refresh keeps whatever the screen already shows rather than blanking a good value. Found next door while fixing it: the catalog book screen set its resume slug only `if (p?.chapterSlug)`, and a PDF read in Original layout is chapterless, so a half-read catalog PDF said "Start Reading" even after a clean mount. The user-book screen had carried a fallback for exactly this since the Original-first work; the catalog screen never got one. That rule is now `resumeChapterSlug` in `packages/shared`, with the dangling-slug case tested, because two copies of a resume rule means one of them is wrong and nothing says which.

## Reader + highlights + tutor — four small places where the screen said more than the data did — backend + web + mobile — 2026-08-28

**Alignment.** The reader opened books ragged-right on mobile and justified-centre on web — the same setting with two different defaults since both shipped. Mobile now matches web, and the drawer keeps all three options for anyone who disagrees. **Highlight context cut mid-word** — mine, from the day before. An anchor stores a raw 30-character window either side of the passage, and I rendered it verbatim, so QA read "…f the weather, with the signs **in** heaven and earth that fore-bo…": the quote begins on the tail of "of" and ends on the head of "forebode". The window itself cannot change — both anchor creators must agree on its size or a highlight made on one client matches worse on the other — so the trimming happens at render. The leading run always goes, because nothing in the text distinguishes the word "the" from the tail of "breathe"; losing one word of context is invisible, starting a quote mid-word is not. A window with no whitespace at all yields nothing rather than a fragment. **"You've seen all of these today"** was said at 00:08 about highlights seen at 14:47 the previous afternoon. The queue is a rolling 24-hour cooldown, not a calendar day, and the same file's docblock already said so — the copy disagreed with the comment above it. It now describes what the server actually does. **The tutor claimed a history that did not exist**, telling a reader "You keep missing this word" about a card created a minute earlier and never answered. Two causes, both ours: `get_due_vocabulary` did not project `totalReviews`, so a brand-new card and one answered wrong twice arrived identically — `consecutiveCorrect: 0`, differing only by a null accuracy that nothing explained; and the prompt's VOICE paragraph literally prescribed the sentence "You keep missing these two", with no condition attached. A prescribed phrase is a claim the model will make whether or not the data supports it. The tool now sends the count and the prompt names the rule: at zero answers the card is new, and saying otherwise is not allowed.

## Mobile — the library filter row stopped depending on fitting a phone — mobile — 2026-08-28

A library with one book showed "All 1 · Reading 0 · Finished 0 · Not started" — three counts and then nothing, which QA read as numbers that do not add up. The numbers were never wrong: `countEntries` returns a full record with `notStarted` in it, tested, and the component renders the chip unconditionally. It was off the right edge of a horizontal ScrollView whose scroll indicator is hidden, so a number you could scroll to looked like a number that was missing. This was the third go at that row, and the file said so itself: the first attempt reordered the tabs and moved the clipping; the second tightened gaps and padding until four tabs plus four chips fitted the ~367dp left beside the view button on a 411dp phone — leaving nothing for a 393dp device, a 375dp one, or a reader who scales their system font. Both attempts were arithmetic against a budget that keeps changing. So the counts leave the tabs entirely. A tab filters; counting is not its job. The number of books you are actually looking at now sits above the list as one line, where it has room to be a sentence and says what you are looking at rather than what you are not. The squeezed metrics go back to ordinary, because a row that fits by arithmetic fits only the device the arithmetic was done on. The failed-uploads tab still appears only when it has something in it.

## Vocabulary — a card says its word out loud instead of waiting to be asked — mobile — 2026-08-28

The owner asked whether the flashcards had sound. They did: a speaker button on every card type, wired to the same TTS the reader uses, and QA verified it at the audio layer rather than by ear — a fourth `AudioTrack` at 24 kHz opening on the process at each tap, with the HAL going to standby after, which is what a stream that actually played looks like. What did not exist was any path where the word is spoken without being asked for: a repo-wide search for `autoSpeak`, `autoPlay` or `autoPronounce` returned nothing, and every card takes speech as an `onSpeak` prop bound to a press. So on the screen whose entire purpose is learning a word, hearing it was a thing you had to notice a small icon to get. It now speaks when the card appears, once per card — keyed on the card, so revealing the answer or re-rendering does not repeat it — with a toggle beside "Auto-save words on tap" in the reader settings, where `ttsSpeed` already lives. `speak` rather than `toggle`, because toggle would stop a previous card's audio if it happened to still be playing, and silence is not what someone who turned this on asked for. A device setting, not an account one, like everything else in that sheet.

<a id="2026-08-28-reader-stopped-writing-a-position-before-restoring-one"></a>

## Reader — the mobile reader stopped writing a position before it had restored one — mobile — 2026-08-28

The other half of the same data loss. Routing a reader to the wrong chapter is recoverable; what made it permanent is that the app then saved that wrong place over the right one, with nobody touching the screen. The WebView posts a `progress` message on its own `load` event carrying `scrollY: 0`, and on the mobile reflow path nothing stood between that and the server — `saveProgress` checked `enabled`, `bookKey` and `chapterSlug`, none of which say whether the reader is where they chose to be. A `restoredRef` existed and no writer read it. Two seconds later, a PUT of zero. The same window opened three other ways: any position load slower than the debounce, leaving a book within two seconds of opening it, and backgrounding the app in that gap — the unmount and AppState flushes were equally ungated. Both of this codebase's other readers already had the answer. The PDF viewer has `pdfPersistGate`, written after exactly this bug in its own form; the web reader keeps `restoredFor` as state rather than a ref, precisely so the save-on-open effect can re-run *after* restore, its comment insisting the offset must reflect the restored scroll "not a transient 0". The mobile reflow reader is simply the one that never got it, and now has it, keyed per chapter because moving on starts a new restore and a single boolean would stay open across the boundary. The gate is a pure function in `src/lib` — where mobile's tests can reach it — and a type predicate rather than a boolean, so extracting the check did not cost a duplicate one beside it. Deliberately not a rule against writing a smaller number: going back is something readers do, and the question is *when* a write is trustworthy, not which way the number moved.

## Settings — a stored default stopped masquerading as a decision, and auto-speak moved to where it is looked for — backend + mobile — 2026-08-28

QA reported the reader's text alignment still defaulting to left, a day after it was changed to centre. Both were true: the default did change, and their device had a stored `reader.settings.v2` blob from before, which the loader spreads over it. The deeper problem is that the two cases are byte-identical in storage — "the reader chose left" and "left was the default when this device first wrote anything" — because every `update` serialised the whole ten-key object, so adjusting the font size froze every other setting at that day's defaults. A changed default could therefore never reach anyone who had ever touched any setting. Only the touched keys are stored now: a new default reaches everyone who never expressed an opinion, and overrides nobody who did. Existing blobs carry no provenance and cannot be reconstructed, so they are honoured in full — which means one manual switch for anyone already on the old alignment, and correct behaviour from here. Alongside: the auto-speak toggle added yesterday sat in the reader's settings drawer while the feature runs on the review screen, two tabs away. QA said people would look for it where the cards are. It moved into the vocabulary settings sheet, and became an account setting rather than a device one — that sheet is server-backed by construction, with a save/cancel contract a device-local toggle would break, and speaking a word is a preference about how you learn rather than about this phone. The migration sets existing rows to true rather than the CLR default, so an account that already has a settings row gets the same behaviour as a new one.
<a id="2026-08-28-reader-continuing-a-book-stopped-erasing-where-you-got-to"></a>

## Reader — continuing a book stopped erasing where you had got to — mobile — 2026-08-28

Read to 10% of chapter two, leave, press "Continue Reading": the reader opened chapter *one* at the top, and seconds later the server held `scroll:1-dramatis-personae:0`, percent 0. The place was gone. Three reproductions, both entry points. The tester guessed the client was sending a stale `chapterSlug`; **no client sends `chapterSlug` at all.** The server derives it by joining the progress row's `chapterId` to the chapters table — and `chapterId` was the chapter the URL named, while the locator was built from the chapter on screen. Mobile's reflow reader appends the next chapter into the same document and never renavigates, so from the moment a reader crosses a chapter boundary the row disagrees with itself: locator in chapter two, id still in chapter one. That split has been there since June; what made it destructive was believing the wrong half on the way back in. The locator is the position and the slug is a projection of a field that stops moving, so the locator now decides — `resumeChapterSlug` reads the slug out of a `scroll:<slug>:<offset>` locator and prefers it, falling back to the stored chapter only when the locator names one that no longer exists (re-parsing renames chapters) or cannot answer at all (a chapterless PDF stores `page:<N>`). That alone repairs rows already written, because their locators were right the whole time. The write side is fixed where the disagreement starts: the id sent with a save is now resolved from the visible chapter's slug, falling back to the route id when the slug names nothing known — a position saved against a slightly stale chapter is worth more than a position not saved. The function also left `pdfResume.ts` for a file that is not named after one format, since living in a PDF-named file is how it came to consider only `page:<N>` locators to begin with.

<a id="2026-08-28-ai-tools-three-ways-an-agent-could-state-something"></a>

## AI tools — three ways an agent could state something the data did not say — backend — 2026-08-28

The tutor telling a reader "You keep missing this word" about a card created a minute earlier turned out not to be one bug. An audit of all eleven agent tools found the same shape repeatedly — **the projection drops the field that distinguishes two states the model is asked to narrate, and the tool's own description asserts the stronger of the two.** Three were fixed here. **The history claim was only half-closed the day before:** the prompt rule guarded `totalReviews == 0`, but a card answered twice and missed twice arrives with `lastAccuracy: 0.0` and sails past it — and `get_weak_vocabulary` described its own results as "the words they keep getting wrong" when the query has no accuracy threshold at all, only an ordering. For a learner whose worst card sits at 90% that description is simply false, and it lives where no prompt fix can reach it. The tool now says it ranks rather than judges, sends `lastReviewedAt` (two misses this morning and two last spring are the same accuracy and a different sentence), and the prompt rule covers "no pattern yet" rather than only "never answered". **Row truncation was invisible while string truncation was not:** `ToolJson.Truncate` has always returned a `truncated` flag that every string-returning tool surfaces, but five row-returning tools did `.Take(limit)` and reported `count = items.Count` — so "12 due" and "the first 12 of 400" were the same JSON, under a field name that asserts the former. They now return `returned` and `hasMore`, fetching one extra row rather than paying for a second COUNT. **And chapter numbers were wrong twice over:** `ChapterNumber` is 0-based, so every reader-facing surface adds one, and long chapters are split into parts that each get their own sequential number with the book's real number preserved elsewhere. Five tools handed the raw ordinal to the model, which cited it — the one part of an AI answer a reader can check by hand, and it pointed at the wrong chapter. Tools now emit a label ("Chapter 8", "Chapter 5 (part 2 of 3)") and the raw ordinal does not leave the server, because there is nothing a model can correctly do with it. One non-truthfulness finding is fixed here too, being a hole in a defence the project had already built deliberately: `get_example_sentence` emitted `bookTitle` unsanitized while `sentence` and the retrieved text beside it were cleaned, and a user-uploaded title is user-controlled text landing in the planner prompt as a tool observation — the sibling tool that sanitizes titles carries a comment saying to treat them as data and never as instructions. What the audit found and this did not fix is written down in STATUS rather than left in a transcript.

## Vocabulary — a Smart session answer is recorded when it is given, not when the session ends — backend + web + mobile — 2026-08-28

QA noticed it while confirming that Smart session answers finally reach spaced repetition at all: after answering the first of two cards the server still showed the old state, and both words moved together after "Session complete". That is because the tutor's only write happened inside the feedback turn, which the clients send when the last card is answered. So leaving a session halfway discarded the work already done — a loss that did not exist a day earlier, because a day earlier the work was discarded either way. `POST /me/tutor/session/{id}/answer` records one answer through the same `VocabularyReviewRecorder` and marks the same applied-word set the feedback path uses, so the closing re-plan still runs and still writes nothing twice. No planner and no LLM call on this route: an answer must not wait on planning to be worth anything, and re-planning per card would be several model calls a session. It carries the feedback path's trust rule too — an id the session never showed is not an answer to it, and is refused rather than recorded. Both clients post it fire-and-forget, because the card has already moved on and a failed write is recovered by the closing call that re-sends everything; the web hook's tests now pin both halves, including that a rejected write does not stall the card.

## Vocabulary — Smart session answers now count — backend — 2026-08-27

The third QA pass answered one card "Knew" in Smart session, watched the summary say "Studied 1 · Accuracy 100%", and then read the word back from the API: `stage: 0`, `consecutiveCorrect: 0`, `nextReviewAt` still in the past, `dueNow: 1`. The card was offered again as a NEW WORD moments later. The control that made it a defect rather than a misreading: the same card answered in ordinary Practice moved `stage: 0 → 1` and pushed the next review out a day. Not even a `VocabularyReview` row, so a Smart session did not count toward the streak either. The session row gained an applied-word set, and that is not defensive decoration: both hooks accumulate results in a ref that is never cleared, so turn two re-sends turn one's answers, and without the set a single "Knew" would have advanced the same card twice and pushed its next review a day further out than the learner earned. Found while wiring it and left alone deliberately: `selfAssessment` is accepted by `SubmitReviewRequest` and read nowhere on the server, so "Almost" and "Forgot" are already indistinguishable in ordinary Practice too — forwarding it from the tutor would have added a second sender of a field nobody reads.

## Highlights — a saved passage is shown inside the sentence it came from, and "review" stopped claiming to be one — backend + web + mobile — 2026-08-27

QA highlighted a single word and every surface rendered it as `"in"` — the reader sheet, the Highlights list, the review card. Nothing about that quote could remind anyone why they saved it. The vocabulary list had solved the same problem a day earlier by showing the sentence with the word emphasised, and the fix had not reached highlights. **The context turned out to be already stored.** A reflow highlight saves a `{prefix, exact, suffix}` anchor with ~30 characters of the real page on each side; `HighlightDto` returns it, and `HighlightListItemDto` and `HighlightReviewDto` simply did not — so the field was dropped at the projection, not at capture, and every existing highlight gains its surroundings retroactively with no migration. The rendering reuses the vocabulary treatment rather than growing a second one: `contextSnippet` moved to `packages/shared`, where its trimming was split from its searching, because a highlight already knows where its passage is and only a word has to be found. PDF-rect anchors and the old no-anchor save path carry no surroundings and cannot be given any; those render as the passage alone, not as an empty frame — the helper returns null for exactly that reason, the same way it does when a vocabulary word is missing from its stored sentence. **The other half is a rename.** The screen called "Review Highlights" showed a passage and a Next button: no question, no recall, no self-assessment, and a summary that nonetheless said "Reviewed 2 highlights". The server cannot hold an answer either — `Highlight` has a single `LastReviewedAt`, the queue is a 24-hour cooldown, and the mark-reviewed request has no field a grade could arrive in. Mobile did not even have the flip that web has; its stylesheet carried a `flipHint` naming one. So it says what it does: Revisit, "You revisited N highlights", and the lightning-bolt icon that promised a drill is now an accessible label describing a page-turner. Real recall for highlights is recorded in STATUS as deliberately not done. Found alongside: the summary counter incremented outside its own `try`, so a run with no network still finished by claiming highlights the server had never heard of.

<a id="2026-08-27-ask-librarian-a-citation-names-its-chapter"></a>

## Ask + Librarian — a citation names its chapter, and the AI screens speak to the reader instead of about them — backend + web + mobile — 2026-08-27

Two defects on the AI surfaces, one shape: the internals reaching the screen. **"ch.0", six times.** An answer cited `[1][6][7][13][14][17]`, six chips appeared under it, and every one read `ch.0` while the chapter was titled "Book I" — so no marker could be matched to any chip. It was tempting to read that as a null leaking through, and it was not: `ChapterOrd` is genuinely 0-based (`XhtmlChapterParser` starts at 0, `IngestionService` copies `Order` to `ChapterNumber`, `BookChunkingService` copies that to the chunk), so `ch.0` really is the first chapter. The chip was simply the one surface printing the stored ordinal — the table of contents renders `chapterNumber + 1`, the footer renders `index + 1`, and the chapter's title was on the client the whole time, matched by the same `citationChapterSlug` that already powers tapping a chip to navigate. It now names the chapter. The second half is the marker: `AskCitation.marker` carries the `[n]` from the answer, mobile discarded it, and mobile deliberately does not make inline markers tappable — so the chip was the only place the two could ever have been joined, and it now leads with it. Web had the identical `ch.{ord}` label through i18n; both clients now share one helper, because a chapter title, a page number and an ordinal are not text that wants translating. **The other leak is a voice.** The librarian told a reader "The user requested short Roman classics about war… No external resources were needed as the library had sufficient on-topic and on-constraint books", and Smart session offered "…keeps the session concise and connected to the learner's recent reading". Both fields are shown on purpose — `TutorPlanView` says so in its own header, "the visible reasoning is the point, not debug text" — and both sit under a heading written in the second person ("Here's your plan, and why"). Nothing in either prompt constrained the register, and the prompts themselves say "the learner" and "the reader" throughout, so the model matched them. Tellingly, both hand-written fallback strings were already first-person: the intended voice existed everywhere except where the model could read it. Fixed in the two prompts rather than in the four screens that render them.

<a id="2026-08-27-mobile-counts-agree-with-their-nouns"></a>

## Mobile — counts agree with their nouns, the streak card stops filling four tabs, and a one-option control is gone — web + mobile — 2026-08-27

Three small things QA could see on one screen each. **"1 words added · 1 words reviewed."** The app had no way to write that correctly: `t(lang, key)` takes a key and nothing else — no parameters, no plural forms — so a count can never reach a translated string. What stood in for a mechanism was five hand-rolled ternaries in five files and thirteen places that hardcoded the plural. `plural(n, one, many, template)` in `packages/shared` replaces both, deliberately covering only English one-vs-many, which is the whole of what ships; real plural categories wait on `t()` accepting parameters, and that limit is now written down rather than rediscovered. Two of the thirteen turned out not to be plural bugs at all and were left alone: "~4 min" is an abbreviation, and "12-day streak" is attributive English, where the noun stays singular however long the streak — the hyphen was the missing piece there, not the s. **The streak card on all four Stats tabs.** It renders once, from a single JSX site — but inside the ScrollView and below the TabBar, under a comment claiming it was "always visible above tabs". It was not above anything; it simply occupied the top of every tab, and at roughly 550pt (a fixed 120pt chart plus a 365-cell heatmap) that is more than half a phone viewport, so on Achievements the first achievement sat below the fold. Web renders it once too, but genuinely above its tab bar — a layout with room a phone does not have. It now belongs to Overview, where the reader's other totals are. **The Language row that did nothing.** A chip row built from `supportedLanguages`, which is `['en']`: one chip, permanently selected, and tapping it called `switchLanguage('en')`, a no-op write of the value it already held. It sat two rows above Theme, where three chips of exactly that shape do work, which is what made it read as broken rather than as "only one locale so far". The precedent was already in the same file six lines below, where "Learning" had been deleted for being the identical thing — with a comment saying a control with one option is not a control. This is that comment again, for the row that was left. The native-language setting next to it is untouched: it is real and it works.

<a id="2026-08-27-deep-links-the-site-can-now-vouch-for-the-android-app"></a>

## Deep links — the site can now vouch for the Android app — web + docs — 2026-08-27

`adb shell am start -d "https://textstack.app/en/books/the-aeneid"` opened Chrome on a device with the app installed, and `pm get-app-links app.textstack.mobile` said why: `textstack.app: 1024`, verification failed. `app.json` has declared `autoVerify: true` for `/en/books*` and `/reset-password*` since the Play launch; Android duly fetched `https://textstack.app/.well-known/assetlinks.json` and was handed the SPA's `index.html` with a 200, because nginx's catch-all `try_files $uri /index.html` answers every unknown path that way — the same soft-404 behaviour already recorded in STATUS as a crawler problem, wearing a second hat. <a id="2026-08-27-progress-a-percentage-now-travels-with-the-unit-it-is-mea"></a>

## Progress — a percentage now travels with the unit it is measured in — backend + web + mobile — 2026-08-27

`ReadingProgress.Percent` and `UserBook.ProgressPercent` are book-wide fractions, and for a long time nothing said so: mobile wrote the fraction of the current chapter, web wrote the fraction of the book, both landed in the same column. The 2026-08-26 QA pass caught the result on one screen without scrolling — the resume card said "The Aeneid — 10% complete" while the same book's row below said 32%, and the server's value was `0.31724`, the fraction read *inside Book II*. #454 fixed the clients, and that did not end it: the column had just been reset by migration and build 21, still running the old JS, filled it straight back in. An installed Android build keeps writing the old unit until its owner updates, and nothing about the number distinguishes the two. So the unit now travels with the value: a client that knows says `percentUnit: "book"`, and a percentage arriving without a declared unit is not stored. Untrusted writes are **not** rejected — the locator, chapter and timestamp are the reader's real position and are saved as always; only the number is left alone, and completion (derived from the number) cannot be triggered by one. A stale build keeps working and keeps its place; it just stops corrupting the column. Applied at both write paths (`UserDataEndpoints.ApplyProgressUpdate`, `UserBookService.UpsertProgressAsync`) and declared by every writer in one place each. Seven existing tests failed the moment the guard landed — they encoded the old contract, in which any number was storable — and were updated to declare their unit rather than deleted, because each represents a current client. Three new tests cover what they used to cover by accident, plus five on the predicate including a `"chapter"` unit that must never be trusted.

## Reader — the WebView stopped reloading itself out from under the reader — mobile — 2026-08-27

QA read to page 17 of a 122-page PDF, left, and the server held `{"locator":"page:1","percent":0.0082}`. Four independent causes, and the largest was not the obvious one. **The document was reloading unprompted:** safe-area insets were dependencies of the `useMemo` that builds the viewer HTML, the reader renders `<StatusBar hidden={!barsVisible}>`, and on Android hiding the status bar changes `insets.top` — while `useReaderBars` auto-hides three seconds after open and toggles on every change of scroll direction. <a id="2026-08-25-reader-six-ways-a-reader-lost-their-place-plus-the-estim"></a>

## Reader — six ways a reader lost their place, plus the estimate that was never built — mobile — 2026-08-25

An adversarial audit of the resume path, prompted by the owner: *"the reading process
must be perfect."* It was not. Every item below was confirmed against the code before
it was touched, and the two most damaging were invisible in any log.

**Progress ran backwards, and the lower value was saved.** The WebView reported
`scrollTop / documentHeight`. But infinite scroll appends the next chapter into the
*same* document, and React Native feeds that number to `computeBookProgress()` as the
*within-chapter* fraction. The moment chapter two landed, standing at the end of
chapter one reported `0.5` labelled "chapter one" — the bar visibly dropped, and the
two-second debounce persisted it to the server. With K chapters loaded, the top of
chapter K reported `(K-1)/K`. The number oscillated for the whole session. Progress is
now computed against the current chapter's own bounds, which the script already
tracked in `chapterSlugs` for a different purpose.

**The saved scroll locator had the same flaw in pixels.** It was an absolute offset
across every appended chapter, restored into a document containing that one chapter
alone. Read into chapter two, stop at absolute 12000 — resume clamps to the bottom of
a chapter you had barely started. The reported offset is now chapter-relative; on a
freshly loaded chapter the two agree, so nothing else changed.

**Offline reading saved nothing at all — 100% of the time.** The offline cache keys
chapters by slug and has no server id to give, so it returns `id: ''`. `saveProgress()`
gated on a truthy `chapterId` and deferred to a replay effect gated the same way, which
therefore never ran. Read three chapters on a plane, close the app, lose every one of
them — and the resume card still showing the pre-flight percent. Offline-first is a
stated pillar of this product; this was the one path where progress was guaranteed lost.
The local write no longer depends on the id; only the server PUT does.

**Chapter navigation overwrote the position it had just saved.** The unmount flush
depended on `saveProgress`, so it fired on every chapter change — with the previous
chapter's closure over refs `navigateChapter` had already zeroed, persisting
`percent: 0, locator: scroll:<old-slug>:0`. Until the destination chapter emitted its
first message, the only stored position was "the chapter you just left, at the top".

**`bookPercent` was erased rather than preserved.** Callers pass `undefined` for "I
don't know yet" — true on every save before the chapter list resolves, and every save
while offline, where it never resolves. `setItem` writes the whole record and
`JSON.stringify` drops `undefined`, so the stored value was deleted; the resume card
fell back to the chapter percent and announced **"85% complete" for a book 12% read**.
The code comment claimed the opposite.

**A PDF never resumed.** Chapterless by design, its position is a `page:<N>` locator
with `chapterSlug: null`. Every consumer looked for a slug, found none, and concluded
the book had never been opened: "Start Reading", routed to chapter one, whose start
page is 1, and the precedence rule *chapter beats server resume page* discarded the
saved page. The locator was written correctly and read on no reachable path. The detail
screen now derives the chapter containing the saved page from the `sourceStartPage`
values the extractor already records, and the precedence rule narrows: a saved page
*inside* the chapter being opened wins. That separates the two ways a reader arrives
without needing a flag — picking chapter 7 from the table of contents opens chapter 7;
Continue routes into the chapter holding the saved page and lands on the page.

**The book being read vanished from Continue Reading at the end of every chapter.**
`ReadingProgress.Percent` is a CHAPTER fraction from mobile and a BOOK fraction from
web, so a bare `1.0` is ambiguous — and a chapter fraction hits exactly 1.0 at the
bottom of any chapter. The `>= 1` exclusion read that as "finished". Exclusion now
requires a percent known to be book-wide, and an ambiguous value is clamped for display.
A finished book lingering is a far smaller error than the current book disappearing at
the moment you want to resume it. Canonicalising the column across web, mobile and the
server shelf is the real fix and is a separate cross-platform change.

**Also.** The reader holds the screen awake — the display timeout fired mid-page, in
the one activity this app exists for (guarded require, so a binary without the native
module simply reads on). PDFs allow pinch zoom: the viewer set `user-scalable=no`, and
on a portrait-locked phone a fixed A4 page renders at roughly 6pt with no way to
magnify it. And "time left", advertised in the settings drawer since it shipped and
never implemented, now exists — `estimateTimeLeft()` over chapter word counts and the
per-user words-per-minute the server has been deriving all along at
`GET /me/reading/pace`, which only web ever consumed.

**Tests: 121 mobile + 258 shared.** The progress reporter is extracted from the HTML
string it ships inside and executed against a fake DOM, so the document-versus-chapter
regression is locked at the source rather than one layer away. `progressStorage` had no
tests at all and now has 13. Two existing tests encoded the old, wrong exclusion rule;
they were rewritten to state the new contract and why it differs, not flipped.

<a id="2026-08-21-ai-24-llm-traces-a-day-were-silently-dropped-postgres-c"></a>

## AI — 24 LLM traces a day were silently dropped: Postgres cannot store a NUL — backend — 2026-08-21

Sentry raised errors, which is how this was found at all. Production logs for the last 24 hours held
468 error lines. Grouped, they were four unrelated problems; this is the largest.

```
Npgsql.PostgresException (0x80004005): 22P02: invalid input syntax for type json
  INSERT INTO llm_traces
  fail: TextStack.Ai.Llm.TracingDecorator
```

24 occurrences, on the `distractor` (6) and `tutor.agent` (2) features — both Ollama-backed.

**The cause.** A NUL byte anywhere in a prompt or a model response is serialized by
System.Text.Json as the six-character escape `\u0000`. That is legal JSON by the specification, and
PostgreSQL refuses it. Confirmed directly against the database rather than assumed:

```
ERROR:  unsupported Unicode escape sequence
DETAIL: \u0000 cannot be converted to text.
```

`llm_traces.messages_json` and `tool_calls_json` are `jsonb`, so the insert throws. It throws inside
`TracingDecorator`'s fire-and-forget writer, which catches and logs — so the only symptom was a log
line and a row that never arrived. Book text extracted from PDFs is a plausible source of stray NULs.

**The fix.** `TraceRedactor.StripNul` removes both forms: the raw character, for the plain `text`
columns (SystemPrompt, ResponseText, Error, which Postgres also cannot store a NUL in), and the escape
sequence, for the already-serialized JSON — a raw NUL cannot survive in serializer output, so the
escape is the only form that reaches `jsonb`. `ToolCallsJson` was bypassing redaction entirely and is
now sanitised too.

Five regression tests, one being the end-to-end shape of the production failure on `distractor`. One
of them caught a bug in *itself* first: the "other Unicode escapes must survive" case had been built
by string substitution that accidentally produced a real NUL escape, so it asserted the opposite of
its own name.

**A wrong theory, recorded because the reasoning is reusable.** The first suspect was
`TraceRedactor.Redact` running email and phone regexes over an already-serialized JSON document — text
surgery on structured data, which looks obviously unsafe. It was reproduced against the real
expressions on realistic payloads, including base64 image data from the vision-RAG path, and it turns
out harmless: every replacement lands inside a quoted string value, so the document stays valid. Two
minutes of testing stopped a plausible-sounding wrong fix.

**Three further problems found in the same logs, not fixed here:**

- `Received backend message BindComplete while expecting ReadyForQueryMessage. Please file a bug.` — 9
  occurrences. Npgsql's own wording for protocol desynchronisation, classically a `DbContext` or
  connection used concurrently from two threads. Worth its own investigation.
- `23505` duplicate key on `ix_reading_progresses_user_id_site_id_edition_id` (2) and
  `ix_reading_sessions_user_id_edition_id_started_at` (2) — the same class as the
  [2026-08-07 postmortem](../incidents/2026-08-07-reading-position-lost-23505.md), which was supposed
  to have closed it. Either that fix is partial or a second path has the same race.
- 18 each of `SocketException (125): Operation canceled`, `IOException: Unable to read data from the
  transport connection` and `NpgsqlException: Exception while reading from stream` — one event seen at
  four layers, most likely clients disconnecting mid-query. Probably benign; 18 a day is worth a look.

- Integration tests: 171 passed, 0 failed. Every one goes over HTTP into the API and through Npgsql

- Unit 1379, Search 20, Extraction 275 — all passing. The search suite is worth naming separately: it

- Live endpoints returning real rows: `/books`, `/authors`, `/search`. Zero `PostgresException` or

## Security — two packages with high-severity advisories, one of them unused — backend — 2026-08-20

Found by reading a build log while fixing something else. `dotnet build` had been printing NU1903 on
every run, and nobody had looked.

**`System.Security.Cryptography.Xml` 10.0.8 — five advisories, and no code used it.** A direct
`PackageReference` in `Infrastructure.csproj`, pinned centrally, referenced by nothing: no `SignedXml`,
no `EncryptedXml`, no import of the namespace anywhere in `backend/src`. `dotnet nuget why` showed it
as a root of the dependency graph with no parent, so it was not there to raise a transitive version
either. Deleted.

**`Microsoft.OpenApi` 2.0.0 — GHSA-v5pm-xwqc-g5wc, high.** Transitive, pulled by
`Microsoft.AspNetCore.OpenApi` 10.0.8. Circular schema references can terminate OpenAPI parsing;
vulnerable from `2.0.0-preview.11` through `2.7.4`, patched in `2.7.5`. Pinned to 2.7.5, held on the
2.x line for compatibility with AspNetCore.OpenApi 10.x.

The tidier mechanism would have been `CentralPackageTransitivePinningEnabled`, and it was tried first.
It pins *every* transitive package to the central list, which immediately turned the build into NU1109
downgrade errors — and in doing so exposed something worth recording: the central `Npgsql` entry is
**9.0.3**, while `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.1 requires **>= 10.0.2**. Resolution has
been quietly upgrading it all along. Nothing is broken today, but the declared version is not the
version that runs, and bumping a database driver is not a change to make in passing. Reverted to two
direct references carrying a comment that says they exist only as a security pin.

Result: `NU1903` count from ten to zero, `dotnet build` at 0 errors, 1379 unit tests passing.

**Also in this change**

*The EF startup warnings are silenced, with the reasoning written down.* Ten
`PossibleIncorrectRequiredNavigationWithQueryFilterInteraction` warnings fired on every boot,
production included: `Edition`, `Author` and `SsgRebuildJob` carry the site query filter and are the
required end of relationships with `BookAsset`, `BookFile`, `Chapter`, `ChapterChunk`, `EditionAuthor`,
`IngestionJob`, `LintResult`, `PodcastGenerationJob` and `SsgRebuildResult`. The hazard EF describes —
a required principal filtered away, leaving dependents pointing at nothing — cannot occur here: the
filter is `x.SiteId == _currentSite.Id` and ADR-007 fixes the deployment to one site with one
`DefaultSiteId`, so it excludes no row that exists. Silenced rather than restructured, because ten
lines of unactionable warning at every boot is how a real warning goes unread. The comment says to
delete the suppression first if multi-site ever returns.

*E2E preconditions now name themselves.* `getTestData()` typed `enBook` as required while
`global-setup` may write `{ siteId: '' }` — so the type lied and the first test to touch it died on
"Cannot read properties of undefined (reading 'slug')". It now throws an error that explains that
global-setup *discovers* books via `GET /books?limit=20` rather than creating them. `fetchBookDetail`
stopped swallowing failures in a bare `catch {}` that became an empty chapter slug and sent reader
tests to a URL with a missing segment. Same family as every other defect found today: a silent
fallback converting a clear precondition into a confusing error several steps downstream.

*Worker logs are captured when E2E fails.* The dump ran `docker compose logs api migrator`. Ingestion
happens in the worker, so when an ingestion-dependent test timed out, the one log that could have
explained it was the one not collected.

*The last two unreferenced EPUB fixtures went.* `test-book-en.epub` and `test-book-uk.epub` had no
consumer, exactly like `test-book-images.epub` deleted alongside the E2E cut. Keeping them would have
been inconsistent with the reason the third one went.

<a id="2026-08-20-web-links-rendered-outside-the-language-provider-pointed"></a>

## Web — links rendered outside the language provider pointed at paths the router does not serve — web + infra — 2026-08-20

Three findings from a sweep of the outstanding bug list, all of the same family: something failing
quietly enough that nothing reported it.

**The cookie banner's privacy link was broken.** It pointed at `/privacy` while every other link on the
same page pointed at `/en/privacy/`. Not a typo — the banner already used `LocalizedLink`. The cause is
structural: `CookieBanner` is mounted as a sibling of the routes, because it has to appear on `/` too
and `LanguageProvider` only exists inside `/:lang/*`. So `useLanguage()` returned the *default context
value*, whose `getLocalizedPath` was the identity function `(path) => path`.

An identity fallback looks harmless and is not: it silently produces a wrong link for every consumer
rendered outside the provider, and a consent banner — the one component guaranteed to render before any
language route — is exactly where the privacy link has to work. The path-building logic now lives in
`buildLocalizedPath`, shared by the provider and the default value, so the fallback prefixes the default
language instead of returning the path untouched. Four tests cover prefixing, double-prefix avoidance,
query-string handling and missing leading slashes.

**Two admin E2E tests had been skipping on every CI run.** `reader-images.spec.ts` calls `adminLogin`
in `beforeAll` and sets `adminAvailable = false` on failure; CI wrote `ADMIN_EMAIL` and `ADMIN_PASSWORD`
into `.env` but nothing ever *created* that account, so the login 401'd and both tests skipped. A skip
still reports green, so the suite looked healthy while the coverage did not exist. The spec's own
comment — "skip all tests if admin not available (e.g. CI)" — shows the hole was known and accepted.

The E2E job now runs `docker compose exec -T api dotnet Api.dll create-admin` after the API reports
healthy. The CLI catches "already exists" and exits 0, so a warm volume does not fail the job.

**The two URLs Google Play holds had no E2E coverage at all.** The delete-account page had assertions
only because someone happened to write them; `/en/privacy` had none. Both are submitted to the store —
the policy is a listing field, the deletion page satisfies the account-deletion requirement — so if
either stops resolving, the listing breaks and nothing else would say so. Both are now in the `@smoke`
gate, checking wiring only: the page exists and rendered its heading. What it *says* stays covered by
the locale parity test, which is the right layer for content.

Smoke is 7 tests now, the non-blocking half still 45.

**Two entries went to `docs/STATUS.md` rather than to code.** Play's Data Safety form still holds the
answers from before the policy rewrite and now contradicts it — the corrected answers are recorded in
the release runbook, but submitting them is a manual Play Console step, and a form that disagrees with
the policy is the worst of the three possible states. And `llm_traces` grows without bound: that is now
a decision rather than an oversight, since the policy says so plainly and account deletion anonymises
rather than deletes, but the table holds prompts and book excerpts, has no cleanup job, and this project
has already lost a night to disk exhaustion.

Verified: 737 web unit tests pass, `tsc -b` clean, and the banner's link reads `/en/privacy/` in a
browser against a production build.

<a id="2026-08-20-mobile-crash-reporting-wired-but-dormant-until-a-dsn-is-s"></a>

## Mobile — crash reporting, wired but dormant until a DSN is supplied — mobile — 2026-08-20

Until now a JS crash on a tester's device produced a fallback screen and a `console.error` that
reached nobody. `ErrorBoundary.componentDidCatch` logged and stopped there; Play Console reports
native crashes and ANRs but never sees a caught React error; and `src/lib/analytics.ts` is a complete
184-line event taxonomy wired to nothing. Entering a 14-day closed test in that state means a tester
says "it crashed" and there is no way to find out why.

Sentry rather than Crashlytics, and it was not close. The backend already runs Sentry across API and
Worker with LLM and provider-routing spans, so mobile joins the same issue stream, and a Book Chat
failure can become one trace from tap to OpenAI call instead of two unrelated haystacks. Crashlytics
would have dragged in Firebase, a `google-services.json` and the Advertising ID question, for a
strictly worse Data Safety posture and a second observability vendor.

**Dormant by default, on the backend's contract.** No `EXPO_PUBLIC_SENTRY_DSN`, no SDK: `initSentry()`
returns immediately and the app behaves exactly as before. Worth knowing the mechanic — Expo *inlines*
`EXPO_PUBLIC_*` at bundle time, so the DSN is baked in when the build or `eas update` runs rather than
read at launch. Confirmed by inspecting the exported bundle: Sentry is present, and the DSN branch has
been compiled away.

**A trap found by building it.** Adding the Sentry Expo plugin made the Gradle release task exit 1:
`sentry-cli` runs during the build to upload source maps and fails outright when `SENTRY_AUTH_TOKEN`
is absent. Left as-is, the owner's next EAS build would have broken on a missing secret with a
confusing error. The plugin now sets `disableAutoUpload: true`, and the runbook says to flip it in the
same change that adds the secret — because without uploads every production stack trace is minified
Hermes bytecode offsets and the integration is decorative. Both switches, one change.

**Scrubbing, because of what this app is.** People read copyrighted and personal books here. A
breadcrumb that innocently records a TTS or translate call carries the passage being read, and
`/api/tts`, `/api/translate` and `/api/explain` all take that text as a query parameter — so the
default behaviour would ship book content to a processor we have not disclosed. `sentryScrub.ts`
redacts `text`, `q`, `word`, `sentence`, `prompt` and `question` from every breadcrumb and request URL
while leaving `page` and `sort` intact, so URLs stay debuggable. Seven tests cover it.

It lives in its own module importing nothing, for a reason worth recording: importing
`@sentry/react-native` into a test pulls in React Native's Flow-typed sources and the transformer dies
with `Expected 'from', got 'typeOf'`. Splitting the rules from the SDK wiring made them testable and
is better design anyway — the rules are the part with decisions in them.

**Also configured:** `dist` from `Updates.updateId`, so "crashing on build 21" and "crashing on
Tuesday's OTA" are distinguishable — without it a JS-only fix looks like it changed nothing.
`sendDefaultPii: false`, no `Sentry.setUser`, no Session Replay: crash data stays in the *not linked
to identity* bucket on the Data Safety form. `Sentry.wrap` on the root layout for touch and navigation
breadcrumbs, and `initSentry()` before provider setup so a failure during startup is still reported.

Verified: `expo prebuild` applies the plugin under SDK 55, the Gradle release manifest task exits 0,
the permission guard still reports 37 permissions with none unsanctioned (Sentry adds none), the
Android bundle exports cleanly at 8.9 MB, `tsc --noEmit` is clean, and 90 unit tests pass.

Turning it on is two owner steps, documented in `docs/03-ops/play-store-release.md`: create a
`textstack-mobile` Sentry project for the DSN, and add `SENTRY_AUTH_TOKEN` as an EAS secret.

<a id="2026-08-20-ci-e2e-stops-gating-production-on-everything-except-smok"></a>

## CI — E2E stops gating production on everything except smoke, and the Chrome download stops flaking deploys — infra — 2026-08-20

Prompted by a fair question — *do we actually need these tests?* — and answered with the repository's
own record rather than with principle.

**What the record says.** 20 of the 70 commits touching `apps/web/e2e` were about flakes, timeouts and
waits: a third of the suite's maintenance went into keeping the suite running. And the one production
incident inside its strongest coverage area — reading position lost to a 23505 upsert race on
2026-08-07, with 13 of 47 tests devoted to progress and bookmarks — was caught by Sentry, not by these
tests. The postmortem is blunt about it: *"Sentry, within hours… This is the incident that paid for the
integration."* A single-threaded Playwright script cannot produce a concurrent write, so that class of
bug was never within reach. The five-week SSG outage was found by a screenshot.

Set against that, the suite does earn something real: it catches broken *wiring*. On this very day it
caught a rewrite of the delete-account page that had silently dropped "This action cannot be undone." —
the one sentence stating irreversibility, on the page a Play reviewer reads.

So the verdict is neither "delete" nor "keep": the shallow part is worth gating on, the deep part is
worth reading but not worth blocking a release for.

**The split.** `smoke.spec.ts` is tagged `@smoke` and gates the deploy — 5 tests: the home page renders,
the catalog lists books, search resolves, an unknown route 404s, the API answers. Cheap, deterministic,
and about wiring only; nothing needing a fixture, a login or a timing assumption belongs in it. The
other 45 run in the same job with `continue-on-error: true`, and a failure raises a workflow warning
plus a job-summary note instead of stopping a release. The Playwright report now uploads on `always()`
rather than `failure()`, since a non-blocking failure no longer fails the job.

**Not done, on inspection.** The plan had been to run the full suite nightly against production. Reading
`global-setup.ts` and the specs killed that: setup uploads test books, and six specs mutate — including
`delete-account.spec.ts`, which deletes accounts. Pointing that at production would create and destroy
real records. And with the full suite already running non-blocking on every PR and every deploy, a
nightly run against an ephemeral stack would mostly re-confirm the same result. Dropped rather than
built.

**The flake that started it.** The deploy that carried the privacy policy was blocked not by a test but
by `storage.googleapis.com` returning 504 while the worker image downloaded Chrome for puppeteer. The
existing guard was three attempts five seconds apart — about fifteen seconds of cover — and all three
burned inside the outage.

Now the npm install and the browser download are separate steps, because they fail for unrelated
reasons at unrelated rates: the install talks to the npm registry and is quick, the download pulls
~150 MB from Google and is the part that flakes. The install runs with `PUPPETEER_SKIP_DOWNLOAD=true`,
and the download retries five times with exponential backoff — 10s, 20s, 40s, 80s, 160s, roughly five
minutes of cover.

One trap avoided along the way. The obvious retry command is
`npx puppeteer browsers install chrome-headless-shell`, since that is what the error named. It would
have been wrong: puppeteer 24 downloads **both** `chrome` and `chrome-headless-shell`, and
`prerender.mjs` calls `launch({ headless: true })`, which resolves to full `chrome` —
`chrome-headless-shell` is only used for `headless: 'shell'`. Installing just the shell would have
produced an image whose SSG could not launch a browser at all: precisely the silent failure that kept
SSG dead for five weeks. The retry therefore wraps puppeteer's own installer, the exact code path that
failed, and the build now asserts `chrome/` exists in the cache rather than merely that the directory
is non-empty.

Verified by building the worker image: both browsers download into `PUPPETEER_CACHE_DIR`, and the guard
passes. Launching Chrome inside the image fails locally with a rosetta error because this is an arm64
Mac and Chrome for Testing ships x86-64 binaries — the same arm64-vs-prod mismatch already documented
for the worker. The downloaded artifacts are identical to before by construction, since the retry
invokes the same `install.mjs` that `npm install` ran as its postinstall.

<a id="2026-08-20-legal-the-privacy-policy-said-data-stayed-in-your-browse"></a>

## Legal — the privacy policy said data stayed in your browser and that nothing was shared; both were false — web + mobile — 2026-08-20

The policy that shipped to Google Play with the internal-testing release contained two claims that
were not merely outdated but the opposite of what the product does:

> "If you choose to use optional features like saving reading progress or bookmarks, this data is
> stored **locally in your browser**."

> "We do not sell, rent, or **share** your personal information with third parties."

Reading progress, highlights, vocabulary and uploaded books are stored server-side and linked to an
account. And book text goes to OpenAI on every AI feature; text goes to Microsoft for speech; looked-up
words go to dictionaryapi.dev; sign-in goes to Google and Apple; email goes to Resend; server errors go
to Sentry; and the website loads Google Analytics and Ahrefs after consent. `CLAUDE.md` even recorded
that the Free Dictionary API was dropped from the mobile reader specifically "to shrink the Play Store
Data Safety third-party processor list to OpenAI + Edge TTS only" — so the list was known internally
and simply never disclosed. It was dated "January 2025", as were the Terms.

A Data Safety declaration that contradicts the policy is a suspension category, not a warning
category, and both had already been submitted.

**What the rewrite says.** Fourteen sections, each mapped to a row that can actually be ticked on the
Data Safety form: scope (site *and* apps); what is collected, split into account, uploaded content,
reading activity, AI interaction data, technical data, and the genuinely device-only preferences; why;
who receives it, naming all nine processors one by one; a section on the AI features; cookies and the
consent gate; storage and security; retention; rights and both deletion routes; children; international
transfers; changes.

Two answers are worth stating plainly because they were the hard ones.

*Sharing.* Sending book text to OpenAI is "sharing" under Play's definition — Files & docs → Shared:
Yes. That is the row most often got wrong, and it is now what both the policy and the form say. The
honest replacement for the old blanket claim is narrower and defensible: we do not sell personal
information and do not share it with advertisers or data brokers.

*Retention.* `LlmTrace` stores `SystemPrompt`, `MessagesJson` and `ResponseText` with a `UserId` — your
prompts and the book excerpts sent as context — and there is no cleanup job anywhere in the backend.
Rather than promise a deletion schedule nobody would run, the policy says what is true: AI interaction
records are kept indefinitely as the operational record of what the service did and what it cost, and
account deletion severs the link (`ON DELETE SET NULL`) so what remains is anonymous. An ugly number
you enforce beats a pretty one you do not.

**Structural fix, so it cannot rot the same way.** Both the web page and the mobile screen used to
hardcode their own sequence of `t()` calls, so adding a section meant editing four files and
remembering all four — which is precisely how one copy of the truth got left behind. The order now
lives in `packages/shared/src/legal/sections.ts` and both clients map over it.

`apps/web/src/locales/__tests__/legalParity.test.ts` holds the line: the `privacy.*` and `terms.*`
blocks must be value-for-value identical between the web locale file and the shared one (Play requires
the in-app policy and the policy at the listed URL to match), every key the section list references
must exist in both, all seven processors must still be named, the retention answer must still be
stated, and the two false sentences must not come back.

That parity check immediately found that Terms had *already* drifted: the mobile copy was missing the
uploads warranty, the indemnity, the DMCA route and the liability cap — seven keys and ten reworded
paragraphs behind the web version, for months, on the platform where users upload books. Mobile now
renders all of it, with the DMCA process linked from both the Terms screen and the profile menu, since
rights holders need a route to it from inside the app that hosts the uploads.

**Delete-account page.** It told a Play reviewer to "open the user menu in the top-right corner" —
the *web* UI. A reviewer opening that URL on Android would go looking for a control that does not exist
there. It now gives both paths separately, and states the timing: deletion is immediate, in one
transaction, with no waiting period and no recovery window.

**Terms** gained an AI section (output is generated, not verified; using the features sends your
selection and its surrounding passage to our providers; how to report a bad response) and a real date.

**Runbook.** `docs/03-ops/play-store-release.md` is new — there was no mobile release runbook at all.
It carries the submitted Data Safety answers verbatim, because Play offers no export and they will be
needed at every future update; the track↔profile mapping; the staged-rollout ladder and the fact that
EAS cannot advance an existing rollout; the fingerprint rule that a native-dependency change needs a
build and not an OTA; and the permission allowlist with its two unresolved WATCH groups.

Verified in a browser, not only by types: all fourteen sections render on the web policy page with the
deletion link live, Terms renders the new AI section without breaking the surrounding markup, and the
delete-account page shows both platform paths. 733 web tests and 83 mobile tests pass.

<a id="2026-08-20-mobile-a-farewell-banner-for-the-frozen-100-runtime-befor"></a>

## Mobile — a farewell banner for the frozen `1.0.0` runtime, before the fingerprint switch strands it — mobile — 2026-08-20

`app.json` set `runtimeVersion.policy: "appVersion"`, which resolves to the literal string `1.0.0`,
while `eas.json` `autoIncrement` bumps only `versionCode`. Every native build ever made therefore
reports the same runtime, and any OTA published to it can land on a binary that lacks the native
modules that update needs. This is not hypothetical: the defensive `try { require(...) } catch {}`
blocks in `useTts.ts:158`, `vocabReminder.ts:41` and `profile.tsx:7` exist for exactly this, and they
degrade features in silence rather than crashing — which is why it has not blown up yet, and why it
would not announce itself when it did.

The fix is `runtimeVersion.policy: "fingerprint"`, which hashes the native inputs — config plugins,
native dependencies, `app.json` — so adding a native module changes the runtime *by construction*
instead of by someone remembering to bump a version string. Discipline you have to remember is not a
fix.

The switch has one cost that cannot be engineered away, only made visible: afterwards, no `eas update`
can ever target `1.0.0` again. Anyone still on an old binary stops receiving updates forever, and
nothing tells them. A silent OTA freeze.

So this is the last thing published to that runtime — a farewell OTA carrying a banner: *this version
no longer receives updates, install the latest from Google Play*. It turns an invisible freeze into a
prompt with a button.

**Order matters, and cannot be compressed.** Publish this to the old runtime *before* the policy
change merges:

```
npx eas update --branch production --platform android \
  --message "Update available from Play Store"
```

Then land the permission/plugin work (it changes the fingerprint), then flip the policy, then build.

**Self-disabling by design.** The gate is `isLegacyRuntime()` in `src/lib/legacyRuntime.ts`: true only
for an updates-enabled Android build reporting exactly `1.0.0`. Builds made after the switch carry a
fingerprint hash, so it renders null on them — the banner is safe to leave in the tree permanently and
costs one string comparison at mount. Expo Go and dev clients report `isEnabled === false` and never
see it. iOS is excluded: the farewell OTA is Android-only and there is no iOS listing to send anyone
to.

The predicate lives in `lib/` rather than inside the component so it is covered by mobile's test
include (`src/lib/**/*.test.ts`). Five tests, because being wrong is expensive in both directions:
too loose and every user on a current build is told to update to the build they already have; too
tight and the stranded users never hear about it, which is the exact silence the banner exists to
break.

A static import of `expo-updates` is safe here even though the codebase guards other native modules
defensively — an OTA is *delivered by* expo-updates, so any build that can receive this code
necessarily has it.

Also in this change: `/slice` deleted. It read a `PLAYBOOK-ai-portfolio.md` that has never existed in
git, and the AI-portfolio phases it was written for are complete. It had also drifted into meaning two
different things — the command file pointed at that playbook, while `.claude/commands/README.md`
documented it as reading UX roadmap briefs. Five dangling references cleaned up with it, including one
in `product-manager.md` that pointed at two more files that do not exist. Note that
`docs/ux-roadmap-v3/` is live (6 slices); the workflow there is now to point Claude at the brief file
directly.

<a id="2026-08-19-reader-the-dyslexic-font-was-a-saved-github-web-page-on-bot"></a>

## Reader — the dyslexic font was a saved GitHub web page on both platforms, so the setting never worked — web + mobile — 2026-08-19

`apps/web/public/fonts/OpenDyslexic-Regular.woff2` was 297,194 bytes that began with eight newlines
and then `<!DOCTYPE html><html lang="en" data-color-mode="auto"...`. It was a GitHub page, curl'd and
saved with a `.woff2` extension. `reader.css` declared it as a real `@font-face`, the browser failed
to parse it, and the "Dyslexic" reader font fell back to sans-serif — no console error, no failed
request, nothing to notice.

The mobile app inherited it by value. `apps/mobile/src/lib/openDyslexicBase64.ts` held 396 KB of
base64 of *those same bytes*, inlined into the WebView reader's `@font-face` by `readerHtml.ts`. The
decoded payload was byte-for-byte the same HTML page. So the accessibility setting had never worked
on either platform, and the mobile JS bundle carried 396 KB of a web page to achieve it.

Both now ship the real font: OpenDyslexic Regular from `@fontsource/opendyslexic` 5.3.0, SIL Open
Font License 1.1, 115,280 bytes, beginning with the `wOF2` signature. The licence text sits next to
it at `apps/web/public/fonts/OpenDyslexic-LICENSE.txt`. The mobile blob is regenerated *from* the web
file by `npm run build:dyslexic-font`, so the two platforms cannot drift apart — or, as here, ship
the same wrong thing twice. It went from 396 KB to 154 KB and started working.

Removing the feature was the other option and the cheaper one. It lost on the grounds that an
accessibility setting which silently does nothing is worse than one that is absent, and fixing it
properly turned out to cost about the same.

**Why nothing caught it for months.** A font is a static asset. No unit test opens `public/`, no
build step validates that a file with a font extension is a font, and a failed `@font-face` degrades
silently by design — that is what a fallback stack is *for*. The failure mode had no output at all.

So there are now two tests that go looking, one per platform:
`apps/web/src/styles/__tests__/fonts.test.ts` reads every file under `public/fonts` and asserts the
`wOF2` signature; `apps/mobile/src/lib/openDyslexicBase64.test.ts` decodes the base64 and asserts the
same, plus that it is not an HTML document and that its size is plausible for a font. The generator
script refuses to run against a source file that is not a woff2. Three checks, because the original
mistake was made once and then copied.

## CI — web unit tests and the whole mobile app were never checked by CI — infra — 2026-08-19

Two gaps found while wiring the font regression tests above, both of the same shape: a test suite
exists, passes, and was never run by anything except a human remembering to.

**The web suite was never in CI.** The `frontend` job ran `pnpm install && pnpm build` for web and
admin and stopped. 100 test files and 731 assertions, invisible to every pull request. A failing web
unit test merged to `main` unnoticed. It now runs `pnpm test` between the build and the overlay
drift-check. All 731 pass today, so this changes nothing about the current tree — it changes what
happens to the next regression.

**The mobile app had no job at all.** `apps/mobile` appeared in `ci.yml` exactly once, as
`pnpm check:mobile-overlay` — a drift check on a generated bundle, run from the *web* working
directory. No `tsc --noEmit`, no unit tests. A mobile type error reached `main` unnoticed, which is
an uncomfortable thing to be true of an app about to go to strangers on a closed track.

There is now a `mobile` job: `npm ci`, `npm run typecheck`, `npm test`. It is a separate job rather
than another step in `frontend` because `apps/mobile` uses npm and its own lockfile, not the pnpm
workspace. `@textstack/shared` is consumed from source through Metro `watchFolders` and tsconfig
paths, so the checkout already carries it and only the app's own dependencies need installing.

Deliberately not included: mobile e2e. `apps/mobile/e2e` is Playwright driving the Expo *web* build
in a Pixel-sized viewport. It exercises no native code path, so running it in CI would buy confidence
it cannot actually provide. (It is also 6 specs, not the 15–16 the docs claim — a separate correction.)

**Turning the web suite on immediately found something.** `readerOverlayMobileBundle.test.ts` lived in
`apps/web/src/lib/` and imported the mobile bundle across the app boundary as
`../../../mobile/src/lib/readerOverlayScript.generated`. That passes on a laptop where someone has
run `npm install` in `apps/mobile` at some point. In CI it failed on the first run: resolving a `.ts`
file under `apps/mobile` makes Vite parse `apps/mobile/tsconfig.json`, which extends
`expo/tsconfig.base` — a module the frontend job never installs, because mobile is npm with its own
lockfile and its own job.

The fix was to move the test rather than install mobile's dependencies twice. It tests a mobile
artifact; it now lives in `apps/mobile/src/lib/` and runs in the mobile job, opting into jsdom with a
`// @vitest-environment jsdom` docblock (mobile's vitest config already supported that — it just
needed `jsdom` as a devDependency). Web is down to 99 files / 726 tests, mobile up to 8 / 78: the
same five assertions, on the correct side of the boundary, and web no longer imports from
`apps/mobile` at all.

Which is the ordinary yield of switching on a check that was never on. The first thing it tells you
is something that was already true.

## Mobile — Play production plumbing: a submit profile that exists, two permissions that shouldn't, and a guard — mobile + infra — 2026-08-19

Three things stood between the Android app and a production submission, and none of them were
visible from the source tree alone.

**A submit profile that did not exist.** `eas.json` had `submit.internal` and `submit.closed`, and
`package.json` had `submit:ios` / `submit:android` scripts pointing at a `production` profile that
was never written. Both scripts had been dead since they were added. There is now a real
`submit.production` at a 10% staged rollout — `releaseStatus: inProgress` plus `rollout: 0.1`, a
fraction and not a percentage, which is the mistake this note exists to prevent. EAS cannot advance
an existing rollout, so 10 → 25 → 50 → 100 stays a Play Console action; re-submitting with a larger
number creates a second release instead of widening the first. Scripts are now named after the track
they ship to: `submit:internal`, `submit:closed`, `submit:production`.

**Two permissions that were never ours.** The app requested `RECORD_AUDIO` and
`SYSTEM_ALERT_WINDOW`, and had done so through every internal-testing build. Neither has a feature
behind it: TTS only plays audio back (`useTts.ts` sets `allowsRecording: false`), and the image
picker is avatar-only. `RECORD_AUDIO` comes from the `expo-audio` / `expo-image-picker` config
plugins. `SYSTEM_ALERT_WINDOW` comes from `expo-dev-launcher` — whose *native module* is
debug-gated, but whose *config plugin* runs at prebuild and writes into the shared main manifest, so
it lands in release builds too. Moving `expo-dev-client` around would not have fixed it.

Both are blocked now, along with `CAMERA`, using two mechanisms on purpose. The plugin props
(`microphonePermission: false`, `cameraPermission: false`) state the intent and reliably suppress the
iOS usage strings; `android.blockedPermissions` emits `tools:node="remove"` and is what the manifest
merger actually honours even if a transitive AAR reintroduces the permission.

**The verification is the interesting part.** `tools:node="remove"` in a source manifest is a
directive, not a result, so the fix was checked against the merged release manifest produced by
`./gradlew :app:processReleaseMainManifest`. All three permissions are absent there.

That merge also exposed how little the source manifest was telling us. The source lists 10
permissions; the merge produces 37. Everything the libraries contribute — `POST_NOTIFICATIONS`,
`WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED`, `USE_BIOMETRIC`, the FCM receive permission — is invisible
until the merger runs, and it is the merged set that Play shows a user.

So `scripts/check-android-permissions.mjs` reads the merged manifest when one exists and falls back
to the source with a warning. It fails the build on any permission not explicitly listed with a
written reason. It was tested in both directions before being trusted: it fails on the pre-fix
manifest, fails again on an injected `READ_CONTACTS`, and passes on the fixed one. A guard nobody has
watched fail is not a guard.

**What the guard found that the audit had not.** 22 permissions are on a WATCH list — reported on
every run, deliberately not blocked yet:

- `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, injected unconditionally by
  `expo-audio`. This app plays TTS in the foreground only — no `UIBackgroundModes`, no media
  service — so they look unused, and `MEDIA_PLAYBACK` is not free: it pulls the app into Play's
  foreground-service declaration flow, which wants a form and a demo video. They are not blocked
  blind, because if `expo-audio` starts a service internally then blocking them turns TTS into a
  `SecurityException`, and TTS is a core feature. That needs a device, not a guess.
- 20 OEM launcher and badge permissions from ShortcutBadger, pulled in transitively by
  `expo-notifications` — Samsung, Huawei, Oppo, HTC, Sony, and friends. The app never sets a badge
  count. On a reading app's listing, "read your settings" and "install shortcuts" read badly.

**Also in this change.** `expo-audio` moves from `devDependencies` to `dependencies`, where a config
plugin that is also a runtime dependency belongs — EAS installs devDependencies, so it built, but it
would have broken the first time a build set `NODE_ENV=production`. And `expo-build-properties` pins
`compileSdk` / `targetSdk` / `minSdk` to 36 / 36 / 24. targetSdk was already 36 by way of the Expo 55
version catalog, so this changes nothing today; it means a future Expo bump cannot silently move the
app off a Play-compliant target without someone approving the diff.

`typecheck` and `check:permissions` scripts exist now. CI does not run them yet — mobile's only
presence in `ci.yml` is still the overlay-bundle drift check.

Verified: `tsc --noEmit` clean, 70 unit tests pass, `expo prebuild` and the Gradle manifest merge
both succeed, guard exits 0 on the merged manifest and 1 on a rogue permission.

<a id="2026-08-11-seo-static-site-generation-had-been-dead-for-five-weeks-a-fo"></a>

## SEO — static-site generation had been dead for five weeks; a forbidden HTTP header killed it — backend — 2026-08-11

> Postmortem: [`docs/incidents/2026-08-11-ssg-dead-five-weeks.md`](../incidents/2026-08-11-ssg-dead-five-weeks.md)

Started from a Bing Webmaster Tools screenshot with four warnings and ended somewhere else entirely. The warnings ("limited crawl capacity", "too many pages with insufficient content") were symptoms; Google Search Console independently agreed (`Crawled – currently not indexed: 780`, `Discovered – not indexed: 311`, `Soft 404: 67` with a validation started 15 May that never passed). Chasing the soft-404 list led to real book and author pages — Pan Michael, The Wings of the Dove, Lew Wallace — not the junk URLs an initial guess predicted.

**Root cause.** `ssg-worker.mjs` calls `http://api:8080/ssg/routes` and deliberately sets a `Host` header so `SiteContextMiddleware` can resolve the site — the file even carries a comment explaining that without it "fetch would otherwise default Host to the URL host (`api`) → 404 → silent job". That mitigation cannot work: **`Host` is a forbidden header name in the fetch spec**, so undici drops it. Verified inside the running container — `fetch` with an explicit `Host: textstack.app` still returns 404. The request arrives as `Host: api`, which is not in `site_domains`, so resolution returned null and the middleware answered `404 Site not found`. Every rebuild job failed. The worker stayed `healthy`, and the only evidence was a log line nobody was watching.

The trigger was refactor R1b, which removed the legacy `?site=` override that had been papering over this.

**Blast radius, measured.** Newest generated page: **3 July**. The sitemap is built live from the database and advertises **1153** book URLs; the generator had produced **764** pages. So roughly **389 published books returned a hard 404 to crawlers** while being actively advertised in the sitemap — which is precisely Google's `Not found (404): 153` and Bing's 140-of-1.3K index.

**Fix.** `SiteResolver` now falls back to the single site (`ICurrentSite.Id`) when the host matches no registered domain, logging a warning naming the host. This is safe in exactly the way the removed `?site=` override was not: that override could name a *different* site, producing a `SiteContext` whose Id diverged from the process-wide `ICurrentSite.Id` that EF's global query filters key on — silently yielding zero rows. Resolving to `ICurrentSite.Id` itself makes divergence impossible, and which hosts can reach the middleware at all is already constrained by `AllowedHosts`. Fixing the resolver rather than the worker also closes the class: any future internal caller that cannot set `Host` (which is every `fetch` caller) now works.

Covered by integration tests rather than unit tests, deliberately: `SiteResolver` depends on the concrete `AppDbContext`, whose model only builds on Npgsql, and the failure was inherently about a real request's host — something a mock cannot express. `SsgRouteResolutionTests` asserts `/ssg/routes` returns 200 for `Host: api`, still works for a known host, and returns a non-empty route list (an empty list would rebuild nothing while reporting success — the same silent-failure shape).

**Two pieces of misleading infrastructure found on the way, worth knowing even though they are not the bug.** `X-SEO-Render` is set from `map $is_bot`, so it reports "you look like a bot", NOT "an SSG file was served" — it says `ssg` even when the fallback ran, which cost real debugging time here. And nginx's `location /ssg/ { internal; alias …/data/ssg/; }` points at a directory that does not exist; `try_files` resolves `$ssg_file` against `root` instead, so the real pages come from `apps/web/dist/ssg` and that block is dead code whose comment asserts it is required.

**This fix alone does not restore the pages** — a full SSG rebuild has to run after deploy for those ~389 books to get generated.

Not addressed here, and separate: the catch-all `location /` returns 200 to bots for any non-SSG path (the bot-404 guard exists only in `@spa`), and Cloudflare's managed `robots.txt` block sets `Content-Signal: ai-input` absent plus `Disallow: /` for ClaudeBot/GPTBot/Google-Extended and friends, which is why Bing reports the site cannot appear in Copilot and grounding results. The latter is a product decision, not a bug.

<a id="2026-08-09-users-entitlement-tiers-replace-two-hardcoded-storage-consta"></a>

## Users — entitlement tiers replace two hardcoded storage constants — backend — 2026-08-09

Triggered by a support case that turned out to be two unrelated ceilings wearing one error message. An upload failed with `Upload failed: 413` while the quota bar read 167.7 MB of 500 MB — plenty of room. **The 413 is Cloudflare's per-request body cap, not our quota**, verified against production by probing with increasing bodies: 10/50/90 MB reached the API (401 — the body got through), 110 MB returned `413 cloudflare`. nginx and Kestrel are both already configured at 500 MB and were never the constraint. That half is fixed separately by chunked upload; this entry is the other half.

The other half: storage limits were two `const`s on `User` (`StorageLimitBytes = 500MB`, `GuestStorageLimitBytes = 50MB`) read through a `user.IsGuest ? … : …` ternary duplicated at the two enforcement sites, and `IsGuest` was the **entire** user taxonomy — `User` has no role column, and `AdminUser` is a completely disjoint table with its own auth, own tokens and no foreign key to `User`. So "give the owner's account 5 GB" was not expressible at all, and neither was any future paid tier.

Introduces `UserTier { Guest, Free, Supporter, Staff }` as a **string** column (house style for new enum columns — readable in psql, immune to renumbering) plus a nullable `storage_limit_override_bytes` for genuine one-offs. Limits themselves live in the new `Entitlements` config section, not in code, so changing a quota is a config edit rather than a deploy: **Guest 50 MB · Free 500 MB · Supporter 2 GB · Staff 5 GB**. The options type deliberately mirrors `BudgetOptions` — root record with `Default` + a dictionary, static `Empty`, accessor-per-field normalizing its own "absent" sentinel, partial inheritance in `Lookup`, pure and never-throws — because that shape already solved this exact problem here and is unit-tested standalone. The binder is the same hand-rolled `AddSingleton` factory: an unknown tier key is skipped rather than thrown, so a typo degrades to the default instead of failing startup.

**The migration backfills `tier = 'Guest'` for existing guests.** The column default is `Free`, which is right for every registered account and wrong for guests — without the backfill, every existing guest would have silently jumped from a 50 MB to a 500 MB allowance the moment this deployed.

Three decisions worth recording. **Staff is granted by `Entitlements:StaffEmails`, not an admin endpoint** — there is no CRUD over site `User` anywhere in the admin app today, and building a management console for a population of one to three is the wrong trade; the config list is reviewable in git, needs no DB write and no new auth surface, and the column remains as a documented manual escape hatch. **The grant is fail-closed for guests**: if `IsGuest`, the allowlist is not consulted at all, because guest emails are synthesized (`guest-{guid}@guest.local`) and one collision must not be able to mint an anonymous 5 GB session. **`MaxSingleUploadBytes` lives on the root options record, not on `TierEntitlements`** — it is Cloudflare's ceiling, not a perk, so "Staff may upload bigger files" is *structurally* inexpressible (there is no key to put it under) and the binder additionally clamps it to a compiled-in platform constant. A test asserts guest and staff receive the identical value.

Two defects the tests caught in this change itself, both fixed. Staff-email normalization initially lived in the DI binder rather than in the options type, so a config entry with a trailing space or a capitalized domain would silently fail to match — and the failure mode (staff quietly not recognized) is invisible; a guarantee outside the type is not a guarantee, since tests and any other construction path bypass it, so it moved into the record. And `GetStorageQuotaAsync` initially kept a separate branch for "user not found", which could drift from what an upload actually enforces; both paths now go through the one resolver, so the quota endpoint cannot disagree with reality.

Also deleted rather than migrated: the `FileUpload:{MaxBookSizeMb,MaxCoverSizeMb,MaxPhotoSizeMb}` config block, which had **zero readers** while `MaxBookSizeMb: 100` read convincingly like the real limit.

`StorageQuotaDto` gains `Tier`, `MaxBooks`, `BooksUsed` and `MaxSingleUploadBytes` so clients can explain a refusal instead of surfacing a raw status code. **1379 unit tests green** (16 new in `EntitlementResolverTests`, covering the guest fail-closed rule, override clamping, and that a mistyped quota of `0` falls back to a working default rather than locking every user out of uploading). Build and `dotnet format --verify-no-changes` clean.

Not in this change: chunked upload (the actual 413 fix), any billing, and migrating the other per-user caps — vocabulary 5000, collections 50, tags 20, avatar 2 MB, agent cost caps — onto tiers. They are catalogued and deliberately left for later rather than folded into one PR with five new enforcement points.

<a id="2026-08-08-worker-provider-readiness-check-circuit-breaker-and-a-sentry"></a>

## Worker — provider readiness check + circuit breaker, and a Sentry environment tag that lied — backend + infra — 2026-08-08

**First, a correction, because this entry exists because of a misread and repeating it would be worse than the bug.** The Sentry issue that prompted this work (`System.Net.Http.HttpRequestException: Name or service not known (ollama:11434)`, 30 events, tagged `environment: Production`) did **not** come from production. It came from a developer machine. Four independent checks: the events report `linux-arm64` (prod is x86_64), release `ee15354c` (a branch commit that was never deployed — prod went `71c6b1da` → `df551f15` → `bb7cfc1c` → `58fec417`), prod's `ollama` container has been `Up 4 weeks (healthy)` with the Worker resolving it to `172.18.0.8`, prod's Worker logged **zero** occurrences of "ollama" in 24 h, and prod has **zero** backfill candidates (`status = Ready AND genre IS NULL`) — every one of its 50 user books has a genre. The "38 starved books" were a local database.

**Why the tag lied, and the fix.** The local `.env` sets `ASPNETCORE_ENVIRONMENT=Production`, so a dev box pointed at the production DSN wrote events into the production Sentry project under a production tag. Anyone reading that UI would conclude "prod", and someone did. `SentryBootstrap.ResolveEnvironmentName` now downgrades a `Production` claim to **`production-unverified`** when `SENTRY_RELEASE` is absent — the release is set from the `GIT_SHA` build arg in both Dockerfiles, so every CI-built image has one and no `dotnet run` ever does. Real production is unaffected. Deliberately a rename rather than a drop: an unverified event is still worth having, it just must not masquerade (filter with `!environment:production-unverified`). `.env.example` gained a warning, and the local `.env` was corrected.

**The hardening stands on its own merits, which are not hypothetical.** Nothing checked provider reachability at startup, so a genuinely dead prod Ollama would fail exactly as silently — `distractor`, `bookmeta`, `tagsuggestion` and every unrouted tag (the Worker's `Ai:DefaultProvider` is `ollama`) degrade quietly. `MetadataBackfillWorker` would spend up to **50 × `Ollama:TimeoutSeconds` (90 s) ≈ 77 minutes** of dead wall-clock per worker start. And worst: `UserBookEnrichmentService.EnrichAsync` stamps **`Completed`, not `Failed`,** when the generator returns null — which is exactly what an unreachable provider produces — so `MetadataEnrichmentWorker`'s 30 s drain would quietly empty the queue into a terminal "done, nothing filled" state that nothing revisits. That last one is provider-independent data loss and was worth the trip on its own.

**What shipped.** `AiProviderReadinessCheck` (replacing `EnrichmentKeyCheck`, whose job it strictly supersedes and whose hardcoded provider set had already drifted — it omitted `openai-pdf`, the most expensive route in the system) probes every provider the route table actually references, once, before any worker loop starts: Ollama via `GET {Ollama:BaseUrl}/api/tags` on a 2 s timeout (the same probe shape the API's `/health/ready` already uses), OpenAI-family by key presence only — **it never spends a token to prove a paid provider is up**. An unreachable provider produces one `LogError` naming the affected tags (`(default), bookmeta, distractor, tagsuggestion → ollama (unreachable)`) plus one Sentry warning, and seeds that provider's circuit open. It can never crash or block the host.

`ProviderCircuitPolicy` is the breaker: pure statics with the clock as a parameter, mirroring `AlarmThrottle` because this repo has no clock abstraction. `OpenedAt` survives escalation, so `JustTripped` is true exactly once per outage — **that single predicate is the whole "one event per condition, not one per retry" requirement**, and it is what turns 30 duplicate events into 1. Backoff 1 → 5 → 30 min (`Ai:ProviderHealth:BackoffMinutes`). Detection lives **inside `OllamaLlmClient`**, beside the three existing `LlmFailureAlarm.Capture` calls, because that is the only place that knows a call died on the wire: the client swallows transport failures and returns an empty response, so a decorator would see success-with-empty and could not distinguish a dead Ollama from a model that said nothing. A **non-2xx deliberately does not trip** — that means Ollama is alive and answering (typically a wrong `Ollama:Model` → 404), fails in milliseconds, and hiding it behind 30 minutes of silence would turn a cheap visible error into an invisible one.

**No silent fallback, in either direction.** Nothing here can move a task to a different provider; `ModelGateway.cs` is not modified at all. Rerouting an outage onto a paid provider is the 2026-07-14 390%-CPU incident with the arrow reversed. Provider choice stays 100% `Ai:Routes`-driven, and the Worker config now states prod intent explicitly instead of implying it.

**Verified against the real failure, not a mock**: local Ollama down, Worker started with `SENTRY_DSN` unset. Before, the backfill would make 38 calls; after, the log reads `enriching 38 user books` → `aborting after 0 enriched / 1 failed — provider 'ollama' is unavailable; the remaining candidates stay queued`, and exactly **one** HTTP request reached the wire (the half-open probe). The 38 candidate rows were still queued afterwards. That per-book re-check was added *because* the first live run exposed the gap: the startup probe opens the circuit on a 1-minute rung while the backfill only wakes at its 2-minute start delay, so the circuit is legitimately half-open by then and a single up-front gate let the whole batch begin. **1363 unit tests green** (79 new across `ProviderCircuitPolicyTests`, `ProviderHealthRegistryTests`, `AiRouteMapTests`, `AiProviderReadinessCheckTests`, `OllamaCircuitBreakerTests`, `MetadataWorkerGateTests`, `SentryEnvironmentTests`), including "20 concurrent callers at `RetryAt` yield exactly one probe" and "30 consecutive failures alarm once". Build + `dotnet format --verify-no-changes` clean. No migration. `Ai:ProviderHealth:Enabled=false` is a kill switch restoring byte-for-byte the previous behaviour.

Both new Sentry events carry explicit fingerprints keyed only on (event kind, provider) — without them `CaptureMessage` groups on the rendered message, which contains the volatile task list and retry duration, so every route edit would spawn a fresh issue and "resolved in release" would never stick.

<a id="2026-08-07-observability-sentry-leaked-sql-a-second-way-ef-core-error-e"></a>

## Observability — Sentry leaked SQL a second way: EF Core error EVENTS, not just breadcrumbs — backend — 2026-08-07

> Postmortem: [`docs/incidents/2026-08-07-sentry-scrubber-leaked-sql.md`](../incidents/2026-08-07-sentry-scrubber-leaked-sql.md)

Caught by the integration's own first day in production. Yesterday's PR (#445) found and fixed EF Core **breadcrumbs** carrying `Executed DbCommand … SELECT …` in their message; that fix was real but incomplete. EF Core also logs a *failed* command at **Error** level, and Sentry's `ILogger` integration turns any Error into an **event** — so the first live capture of the (separately real) `PUT /me/progress` failure arrived with `INSERT INTO reading_progresses (id, chapter_id, edition_id, locator, max_chapter_number, percent, site_id, updated_at, user_id) VALUES (@p0, …)` inline in the event message. Two distinct channels, one shared assumption: that nulling the structured `data` bag was where the SQL lived. It never was — EF interpolates the statement into the human-readable text on both paths.

Scope of the exposure, stated precisely: **no parameter values ever left the process** — `EnableSensitiveDataLogging` is off, so EF renders `@p0` / `'?'`, and Npgsql itself writes "Detail redacted as it may contain sensitive data" on the inner `PostgresException`. What did leave was statement shape and schema (table and column names). No book text, no reader identity. Still a promise this integration explicitly made and broke, and schema disclosure to a third party is not free.

Fix: `SentryScrubber.Scrub` now drops any event whose `Logger` starts with `Microsoft.EntityFrameworkCore`, plus a message probe for `Executed DbCommand` / `Failed executing DbCommand` so a re-categorised logger can't reopen the hole (`SentryScrubber.IsDatabaseCommandEvent`). **Dropping loses no signal**, which is what makes it the right call rather than a redaction exercise: the same failure is already reported by `ExceptionMiddleware` as a `DbUpdateException` carrying a full stack trace, the Npgsql SQLSTATE (`23505`) and the violated constraint name — everything needed to debug it, none of the SQL. A test locks that the middleware event survives while the EF command event dies.

The generalisable lesson, and the reason this is worth a CHANGELOG entry rather than a quiet patch: **a scrubber written against one egress path will be bypassed by the next one.** The original design rejected Sentry's OpenTelemetry exporter precisely because it bypasses `BeforeSend` — then shipped with two log-pipeline channels doing the same thing from the inside. Unit tests were green throughout both, because they asserted the scrubber's behaviour on the input shape we imagined rather than on what the SDK actually assembles. Only reading a real captured event found either one.

**1284 unit tests green** (3 new), build + `dotnet format --verify-no-changes` clean. No migration, no config, no behaviour change when `SENTRY_DSN` is unset.

<a id="2026-08-07-reader-reading-position-was-silently-lost-on-concurrent-save"></a>

## Reader — reading position was silently lost on concurrent saves (23505 upsert race) — backend — 2026-08-07

> Postmortem: [`docs/incidents/2026-08-07-reading-position-lost-23505.md`](../incidents/2026-08-07-reading-position-lost-23505.md)

Found by Sentry on its first day in production, which is the point of having installed it. `PUT /me/progress/{editionId}` was throwing `Npgsql.PostgresException: 23505: duplicate key value violates unique constraint "ix_reading_progresses_user_id_site_id_edition_id"` — ten times in four hours, from real readers, returning a 500 and **dropping the reader's position in the book**. Nothing crashed, no test failed, and the only prior symptom would have been a user saying "it forgot where I was".

Root cause is a textbook read-then-insert with no concurrency control: `UpsertProgress` queries `ReadingProgresses` for the row, and inserts when it finds none. One reader legitimately produces overlapping writes — the 30s session heartbeat, a `sendBeacon` on unload, an offline-queue flush after reconnect, or simply a second device — so two requests both see no row, both `INSERT`, and the loser violates the unique index. The window is milliseconds wide, which is why it only appears at real traffic and never in a test.

Fix: catch the unique violation and merge into the winner's row instead of failing. On `DbUpdateException` with SQLSTATE **23505** (matched via `PostgresErrorCodes.UniqueViolation`, not a message string, so it survives locale and constraint renames) the doomed insert is detached, the winner is re-read, and the client's write is applied to it — the exact update path we would have taken had we lost the race by one more millisecond. Critically, **the stale-write guard is re-applied against the WINNER's timestamp**, so recovering from the race still cannot move a reader backwards; and the monotonic `MaxChapterNumber` high-water mark (which feeds the RAG spoiler gate) is raised through the same shared `ApplyProgressUpdate` helper used by the normal path, so the two can never drift. A unique violation with no winning row (e.g. deleted in between) is rethrown rather than silently swallowed — that is not the race we know how to recover from.

Chosen over a native `INSERT … ON CONFLICT DO UPDATE` deliberately: the endpoint's semantics include an early return that echoes the *existing* row back when the client's timestamp is stale, which does not express cleanly in an upsert statement, and rewriting a hot path into raw SQL to fix a millisecond race is more risk than the race. The retry keeps every existing behaviour and touches one method.

**1289 unit tests green** (9 new, locking the high-water-mark monotonicity, the NULL-vs-ordinal-0 seeding rule, and that the recovery triggers on 23505 and nothing else — a foreign-key violation must still surface). Build + `dotnet format --verify-no-changes` clean. No migration.

<a id="2026-08-06-observability-sentry-for-api-worker-with-llm-agent-and-provi"></a>

## Observability — Sentry for API + Worker, with LLM agent and provider-routing spans — backend + infra — 2026-08-06

TextStack had **no error tracking at all**. OpenTelemetry has been wired since feat-0005, but it exports to an `aspire-dashboard` container that is profile-gated **off in production** — so for the whole life of the AI stack, prod telemetry has been going nowhere and nobody was alerted on anything. The trigger for fixing it was the 2026-07-14 incident (entry below): the Worker's `Ai:Routes` had no `pdf.parse` entry, so the user-PDF vision parse fell through to `Ai:DefaultProvider: ollama` and pegged the CPU-only Ollama container at **~390% for ~42 s/page across a 106-page book**. Nothing threw, nothing logged an error, no OpenAI traffic appeared, and the job simply produced zero chunks. **The failure mode was silence, and silence is exactly what a monitoring stack has to be taught to notice.** A reader of the write-up suggested emitting the resolved provider as a span attribute; that suggestion is the core of this change.

**The routing spans.** `ModelGateway.Route` and `ModelGateway.ResolvedPrimaryKey` each independently recomputed the same precedence — registry Primary → `Ai:Routes:{feature}` → `Ai:DefaultProvider` → literal `"openai"` — and neither could tell a *deliberate* route from a *silent* fallback, because the whole thing was one `??` chain that collapsed both into a string. Both now go through a single `ResolveRoute()` returning `(Key, Reason)`; the key expression is unchanged, so the resolved provider is provably identical (locked by a precedence theory in `ModelGatewayRouteReasonTests`). Every gateway call now attaches `ai.task`, `ai.provider.resolved` and `ai.provider.reason` (`route_matched` | `default_fallback`) to the ambient span — on the Sentry span *and* the OTel `Activity`, so the answer to "which model actually served this, and did anyone choose it on purpose?" comes from a trace instead of from a CPU graph. On top of that, an **expensive** task landing on `default_fallback` raises a Sentry warning outright: falling back to the default is normal and correct for most features, but for `pdf.parse`, `rag.summarize` and `podcast.script` (config `Ai:RouteAlarm:AlertOnDefaultRouteFor`) it is a defect by definition. **Throttling is load-bearing, not polish**: `pdf.parse` resolves once per page with parallelism 6, so that 106-page book would have raised 106 identical events — `AlarmThrottle` dedupes per `(task, provider, reason)` on a 60-minute cooldown (`Ai:RouteAlarm:CooldownMinutes`) while still firing the *first* hit immediately, so a bad deploy is visible within one page.

**Agent + RAG spans.** `AgentLoop.StreamAsync` is the single seam every agent runs through — Enrichment, Librarian, Tutor, StudyBuddy and the crews — because `RunAsync` is pure delegation, so one `using var trace = TraceScope.Start("agent.run", "ai.agent")` covers all of them (`using` is legal in an iterator and disposes on completion, `yield break`, throw *and* consumer abandonment). Each run reports `agent.name` (the `FeatureTag`, which is both the agent identity and the key `Ai:Routes` is indexed by, so the tag joins with routing config), `agent.model`, and measures for iterations/tokens-in/tokens-out/cost/duration; the outcome defaults to `error` and is set to `completed` or `budget_exhausted` at the three terminal paths, mapping 1:1 onto `AgentRunRecordFactory`'s statuses. `RagIndexingService` opens a `rag.index` span per book **after** the atomic claim (a lost claim is the common no-op and emits nothing) carrying `rag.kind`, `rag.book_id` and `rag.chunk_count`, and both `FailUserBookAsync`/`FailEditionAsync` — the single choke point for `rag_status = 3` — now raise a Sentry error carrying the `rag_error`. One deliberate exception: **`"indexing interrupted, retry"` is never sent**, because it fires on every deploy that lands mid-index and the sweep re-queues it — paging on a self-healing state on every release is how alerting dies.

**Provider failures.** `OllamaLlmClient` swallows non-2xx, timeouts and transport errors and returns an empty zero-token response — which is load-bearing (callers depend on it), and is precisely why those failures are invisible in `llm_traces`: `TracingDecorator` only ever sees a successful, empty answer. The swallow is untouched; each of the three branches now also calls `LlmFailureAlarm.Capture` with `ai.provider` / `ai.task` / `ai.failure` tags, on the same throttle. OpenAI failures need no such handling — they propagate to `TracingDecorator`'s two non-cancellation catches, the single choke point, which now reports them with the provider key (threaded in as a trailing optional ctor param so no existing test construction churned). Cancellation stays excluded on both paths: an SSE client disconnecting is not a model error.

**Why not `Sentry.OpenTelemetry`.** The obvious move — bridge the existing OTel spans into Sentry so there is one instrumentation — was rejected on evidence. Sentry deprecated that package, and its replacement (`Sentry.OpenTelemetry.Exporter`, on beta OTLP ingest) ships spans through the *OpenTelemetry* SDK, meaning `BeforeSend` never sees them. Our OTel spans carry `http.client_ip` (`ServiceCollectionExtensions.Hosting.cs`) and full SQL text (`SetDbStatementForText = true`), and there is no hook to strip either on the way out — that is a hard blocker for a reading app. It would also have forced Sentry's sample rate onto the shared `TracerProvider`, coupling the cost knob to the Aspire pipeline. Instead `TraceScope` dual-writes: one `Activity` (→ OTLP/Aspire, one added `AddSource` line is the *only* change to the existing pipeline) and one Sentry span (→ scrubbed at the edge).

**Noise and privacy.** `SentryScrubber` is an **allowlist, not a denylist** — every tag and extra not explicitly blessed is dropped or redacted. A denylist only stops the leaks someone remembered to enumerate; with an allowlist a future `span.SetTag("prompt", userText)` dies at the edge whether or not a reviewer caught it. On top of that: `SendDefaultPii = false`, `MaxRequestBodySize = None` (uploads are books, POST bodies are reader prompts), user identity blanked, `Authorization`/`Cookie`/`X-Admin-*` headers stripped, free text run through the existing `TraceRedactor` and truncated to 512 chars, breadcrumb `data` bags dropped wholesale, and `/health` + `/health/ready` sampled at 0.0. Client-error exceptions (`NotFoundException`, `ConflictException`, `ValidationException`, `DomainException`, `BudgetExceededException`, cancellation) are dropped — none can reach Sentry today because `ExceptionMiddleware` maps them to 4xx *without logging*, but the filter guards a future `LogError` on a validation path. Rate-limiter 429s are not exceptions and were never in scope. Sampling is deliberately asymmetric: `http.server` at `Sentry:TracesSampleRate` (0.2 prod, 1.0 dev), but `ai.agent` and `rag.index` **always at 1.0** — they are rare and they are the entire reason for this integration; sampling them at 0.2 would discard four of every five traces we added Sentry to see.

**Wiring and the no-op guarantee.** API takes `Sentry.AspNetCore` (6.8.0 ships a first-class `net10.0` TFM with zero dependencies); the Worker is a generic host with no request pipeline, so Sentry rides the ILogger provider — additive, the OTLP logging provider is untouched. Both call sites **skip the SDK entirely when `SENTRY_DSN` is empty** rather than initialising with a blank DSN (which still installs middleware and logs a startup diagnostic), so local dev, CI and forks are byte-identical to before. All the seam code (`SentrySdk.CaptureMessage`, `GetSpan`) is already inert against a disabled hub, so no `if (enabled)` guards leaked into `AgentLoop`, `ModelGateway` or `RagIndexingService`. `MinimumEventLevel = Error` is what actually captures unhandled errors: `ExceptionMiddleware` catches everything and returns a 500, so nothing ever reaches Sentry's own middleware — errors arrive via its `logger.LogError(ex, "Unhandled exception")`, confirmed in the verification below (the captured event's `logger` tag reads `Api.Middleware.ExceptionMiddleware`, `mechanism: SentryLogger`). Release plumbing is six lines of infra and no C#: `ARG GIT_SHA` → `ENV SENTRY_RELEASE` in both Dockerfiles (declared after the publish copy so a new SHA invalidates only that trivial layer, not the .NET build or the ~150 MB puppeteer install), `build.args` in compose, and `export GIT_SHA=$(git rev-parse --short HEAD)` in `deploy.yml` — `.dockerignore` excludes `.git`, so the build arg is the only way the SHA can get in, and without a release Sentry cannot do regression detection or tell you which deploy an issue started with.

**Verified end-to-end against the real DSN**, not just unit-tested: `POST /admin/diagnostics/sentry-test` (admin-gated by the existing path-based middleware; 401 unauthenticated) returned `{"eventId":"68aa5de7…","enabled":true}` and the API logged the same id; `POST /admin/diagnostics/sentry-test-error` returned 500 and produced a Sentry issue tagged **release `71c6b1da`, environment `Production`**, with `logger: Api.Middleware.ExceptionMiddleware` and only `Accept`/`Host`/`User-Agent` in the request headers — **the admin session cookie the request carried is absent**, user is empty, no body. A synthetic routing event confirmed the allowlist on the wire: `ai.task=pdf.parse`, `ai.provider.resolved=ollama`, `ai.provider.reason=default_fallback` survived; a `prompt` tag was **gone** and a `response` extra came through as `[redacted]`; an exception message containing an email arrived as `TextStack verify: synthetic failure for [redacted-email]`. One honest caveat: Sentry still shows a coarse **Geography (city-level)** derived server-side from the ingest connection IP — that is inferred at their edge, not sent in our payload, and in production it resolves to the datacenter rather than a reader. **1281 unit tests green** (35 new across `SentryBootstrapTests`, `SentryScrubberTests`, `AlarmThrottleTests`, `ModelGatewayRouteReasonTests` — including `TryEnter_RepeatedWithinCooldown_ClaimsOnce`, which replays 106 page-parallel calls and asserts exactly one event), `dotnet build` and `dotnet format --verify-no-changes` clean. No migration. No changes to web or mobile.

**Two findings from running it for real, both fixed/known before merge.** First, the scrubber leaked SQL. Pointing the local Worker at the branch build surfaced a genuine failure — the Ollama container wasn't running, so `MetadataBackfillWorker` threw 38 transport errors — and the resulting Sentry event's **breadcrumb trail carried `Executed DbCommand … SELECT m.feature_tag … FROM models`**. EF Core puts the SQL in the breadcrumb *message*, so nulling the structured `data` bag did nothing; this is the same `SetDbStatementForText` class of leak the PR avoided by rejecting Sentry's OTel exporter, quietly re-entering through the log pipeline. Fix: `ScrubBreadcrumb` now **drops EF Core command breadcrumbs entirely** (by category or by an `Executed DbCommand` message probe) rather than redacting them — a diagnostic breadcrumb is not worth shipping query text about what people are reading to a third party. Re-verified on a fresh live event: no `DbCommand`, no SQL. Second: those same 38 failures produced **exactly one Sentry event**, tagged `ai.provider=ollama`, `ai.task=bookmeta`, `ai.failure=transport` — the throttle working against a real running process rather than a unit test, and a failure mode that produced zero visibility before this PR. **To be exact about provenance, because the event itself is not:** this was a developer machine, not production — prod's `ollama` service was healthy throughout. The event nevertheless arrived tagged `environment: Production`, because the local `.env` sets `ASPNETCORE_ENVIRONMENT=Production`. That mislabelling is a real defect in its own right (a dev box writing into the production Sentry project under a production tag) and is fixed separately; it is called out here so nobody later reads this entry as a production incident.

**What we expect it to catch first**, in order of likelihood: a `default_fallback` on `rag.summarize` or `podcast.script` in the Worker (the same class of config drift as the original incident, now audible); Ollama timeouts during vocabulary distractor generation, which are today completely invisible because the client swallows them; and terminal RAG indexing failures on user PDFs, which until now surfaced only as a book stuck on a badge in the UI.

**Owner step:** `SENTRY_DSN` must be added to the prod `.env` by hand before the first deploy that ships this — deploys go through GitHub Actions and the server `.env` is not managed by them. Until it is set, Sentry stays off in production, which is the designed safe outcome.

## RAG — deterministic tie-breaker on retrieval ORDER BY (repo now matches the article) — backend — 2026-07-15

The published RAG-determinism article claims hybrid retrieval orders with a deterministic tie-breaker (`ORDER BY score DESC, id`) — an audit found the fix was **missing from the repo**: all four hybrid queries in `RagService` (catalog + user-book, vector + lexical) ordered on the raw score/distance alone. That's a real (if quiet) nondeterminism: `ts_rank_cd` ties are common and float-distance ties occur on duplicate chunks, so tied rows at the `LIMIT` cutoff swap between runs (Postgres heap-order dependent) → a different fused chunk set → different citations/answers for the same question and flaky `recall@k` evals. All four ORDER BYs now carry `, id`; the catalog SQL was extracted to a testable `BuildCatalogSql()` (mirroring `BuildUserBookSql`) and a new `RagServiceDeterminismTests` locks the invariant so a future edit can't silently drop it. **Deliberately NOT changed** (reported instead): the whole-table ANN scans in `HybridCatalogSearch`/`SimilarBooksService` — pgvector serves an index-assisted scan only for a pure distance ORDER BY, so adding a secondary sort key there would silently turn indexed ANN into a full scan; the per-edition/per-book RagService queries are small filtered scans where the tie-breaker is free. `RrfFusion` untouched (already deterministic — stable sort, first-seen tie order). **1185 unit + 20 search** tests green.

<a id="2026-07-14-reliability-a-slow-hung-rag-parse-can-no-longer-wedge-the-in"></a>

## Reliability — a slow/hung RAG parse can no longer wedge the indexing worker — backend — 2026-07-14

> Postmortem: [`docs/incidents/2026-07-14-rag-parse-wedged-worker.md`](../incidents/2026-07-14-rag-parse-wedged-worker.md)

Follow-up to the durable-indexing work: the sweep loop `await`ed each book's chunk (vision parse) **inline**, so one slow or hung parse blocked the whole loop — no drain, and critically no stale-reclaim — until it returned. The mis-routed 74-minute Ollama parse wedged the worker exactly this way. Now the sweep **detaches** the parse to a background `Task.Run` gated by a `SemaphoreSlim(1)`: it dispatches at most one parse at a time (bounds paid vision spend) and the loop keeps running stale-reclaim + drain checks every 30 s, so a stuck parse can't wedge it. A **hard parse timeout** (`Ai:Pdf:ParseTimeoutMinutes`, default 12, clamped below the 15-min stale window) terminates a live-but-slow parse to `Failed`/"indexing timed out, retry" before the stale sweep would — and the render phase now honors the token too, not just the vision calls. Restart-safe (the atomic `rag_indexing_started_at` claim runs before the parse, so a killed detached task is recovered by the stale sweep). **Hardened by adversarial QA** — the review caught (and this fixes) a **HIGH** semaphore leak: a DB exception between `Wait(0)` and dispatch would have leaked the slot permanently → the very silent-worker-wedge the change set out to kill; now a `try/finally` releases the slot on every non-dispatched path. `dotnet build` + **1120 unit** tests green. Live parse verified on prod earlier (OSCE: 375 chunks → Ready in ~4 min on gpt-4.1); the detach/timeout paths are unit-tested where pure and reasoned through for concurrency (no local OpenAI key / arm64 SIGILL).

## Reliability — "Ask this book" indexing no longer gets stuck + reading sessions survive a deleted book — backend + web — 2026-07-14

Two prod-confirmed reliability holes. **"Ask this book" could stick on "Preparing… 0/0" forever.** `POST /me/books/{id}/index` (and the catalog twin) atomically claimed `NotIndexed/Failed → Indexing`, then ran the chunking — for a PDF the **minutes-long `PdfVisionParser` vision parse** — **synchronously inside the HTTP request**, only returning `202` once it finished. When that request died (Cloudflare ~60-100s timeout, or the API container restarting on deploy — which is exactly how the OSCE workbook got stuck), the row was left `Indexing` with 0 chunks and **no terminal `Failed`**; the claim only re-claims from `NotIndexed/Failed`, so `Indexing` was a permanent dead end. Fixed by moving chunking **off the HTTP path into the Worker**, mirroring the enrichment-reliability pattern: the endpoint claims and returns `202 Indexing` immediately; a `RagIndexingService` executor does the work under an atomic `rag_indexing_started_at` claim and **always reaches a terminal state** (`chunkCount==0` / exception / cancellation → `Failed`); a `RagIndexingWorker` sweep (30s, one book/cycle to bound paid vision spend) drains queued books and reclaims dead-process `Indexing` rows (`started_at` older than 15 min) → `Failed`. The `ChapterEmbeddingWorker` chunk→embed→`Ready` hand-off is unchanged; catalog and user-book paths unify on the one executor. Migration adds nullable `rag_indexing_started_at` (+ partial sweep indexes) on `user_books` + `editions`. **Hardened by adversarial QA**: the embedder now marks a book `Failed` when it permanently poisons a chunk (previously `embedded < chunk_count` stranded it `Indexing` forever, bypassing the `chunk_count=0` sweep); the executor's chunk-count stamp is a guarded `WHERE rag_status=1` UPDATE (a stale-swept `Failed` row can't be clobbered); `embedded_count` is recomputed from actual rows after chunking (was a blind `0`, losing an embedder-drains-first race); and cancellation writes "indexing interrupted, retry" instead of a misleading "no chapters". Known follow-up (accepted): full concurrency/detach for a multi-Worker deployment (the model assumes a single Worker today).

Separately, **reading sessions for a deleted book stopped flooding 500s.** After re-uploading a book (old id gone), the client's queued/`sendBeacon` sessions kept resubmitting for the dead `user_book_id`, hitting a Postgres `23503` FK violation → unhandled `DbUpdateException` → 500, retried forever. Now `ReadingSessionService.SubmitAsync` existence-checks the referenced book (owned + live user book, or a real edition) and returns **404** for a gone book (with a belt-and-suspenders `23503` catch → benign ack), and the client **prunes** the queued session on a 404 instead of re-queuing it (5xx/network still retry). `dotnet build` + **1113 unit** tests (+ session/RAG integration tests: `202 Indexing`-without-chunking, session `404`); web `tsc`/`vite build` + **684 web** vitest. The live chunk→embed→`Ready` round-trip verifies on prod (arm64 worker SIGILL + no local OpenAI key); already-stuck prod rows are cleared by a one-off backfill at deploy.

## Ops — root cause: the nightly backup was leaking 156 GB of orphaned pgdata volumes — infra — 2026-07-10

> Postmortem: [`docs/incidents/2026-07-10-backup-leaked-156gb.md`](../incidents/2026-07-10-backup-leaked-156gb.md)

The actual root cause behind the flapping backup (the self-diagnostics below were added to *find* this). Prod's Docker data-root lives on a **separate `/mnt/data` partition** (not `/`, which `df -h /` alone hides) and it had hit **100% / 0 bytes free** — 183 GB used, **156 GB of it 57 dangling anonymous `pgdata` volumes**. `backup-verify.sh` spins a throwaway `pgvector` postgres each run; postgres declares an anonymous `VOLUME /var/lib/postgresql/data`. On a killed/timed-out run `--rm` never fired and the cleanup did `docker rm -f` **without `-v`** → one full pgdata volume leaked per run. 34 days × daily ≈ 156 GB → the docker root filled → a fresh throwaway postgres could no longer `initdb` → **the backup broke the very verify step that had been creating the volumes** — a self-reinforcing failure. Real prod data was never at risk (postgres + storage bind-mount to `/`, which was at 61%); only the anonymous verify volumes bloated `/mnt/data`. Fix: `docker rm -f` → **`docker rm -fv`** (both the trap cleanup and the leaked-container reap) so the anonymous volume dies with its container, plus a `docker volume prune -f` catch-all for SIGKILL'd runs the trap can't cover (named volumes are untouched by prune). Remediated live: `docker volume prune` reclaimed **163 GB**, `/mnt/data` 100% → 17%. Diagnosed the hard way — the box was also unreachable for a stretch (a clean manual reboot, not a crash; a full disk still lets you SSH in, so an SSH *connect*-timeout is a host-offline signal, not disk).

## Ops — backup verify self-diagnoses failures + reaps leaked containers — infra — 2026-07-10

## Auth — fix spurious "Unauthorized" mid-session (refresh-token stampede) — web — 2026-07-09

> Postmortem: [`docs/incidents/2026-07-09-refresh-token-stampede.md`](../incidents/2026-07-09-refresh-token-stampede.md)

Fixed the reader dead-ending on **"Error loading chapter — Unauthorized"** after ~an hour, even though the user was still signed in (Google/email). Root cause: the access token expires at 60 min, and the reader fires many authenticated requests in parallel (chapter, book, progress, bookmarks…), so they all 401 at the same instant and each independently called `/auth/refresh`. The server **rotates** the refresh token on every refresh (deletes the presented token, issues a new one), so only the first concurrent refresh won — the rest presented the now-deleted token and got 401, surfacing as a spurious mid-session logout. Fix: `refreshToken()` in `apps/web/src/api/auth.ts` is now **single-flight** — concurrent callers share one in-flight `/auth/refresh`, so there's exactly one rotation and one fresh cookie, then every caller retries. This makes silent refresh reliable, so an active user stays signed in across the full rotating refresh-token window (i.e. until they explicitly log out or are inactive past the TTL) instead of being bounced hourly. Pure client change, no backend/token-config change. `tsc` clean, `vite build` green, **22 auth/api vitest** green (3 new: concurrent-dedup, fresh-request-after-settle, lock-clears-on-failure). Mobile (`apps/mobile/src/lib/api.ts`) already single-flights refresh — not affected.
